## 3. Decisions taken in this brief

### 3.1 Toolchain: Go 1.27.4

Source: the official release list, `https://go.dev/dl/?mode=json` (read 2026-11-11 01:35 UTC): the two supported
stable releases are `go1.27.4` and `go1.26.11`. Release history `https://go.dev/doc/devel/release` (same date):
go1.27.4 released 2026-11-10 "includes security fixes to cgo, the go command, the compiler, the linker, and the
net/http package"; go1.27.0 released 2026-08-19. Release notes `https://go.dev/doc/go1.27` and `go1.26`, *Ports*
section: no change for linux/amd64, arm64, arm, mips, mipsle (only macOS 13 minimum and ppc64 ELFv2).

`go.mod` of the main module:

```
module nmb

go 1.27.0

toolchain go1.27.4
```

Why 1.27 and not 1.26: both are patched today; 1.26 leaves support when 1.28 ships (the Go policy keeps the two
newest majors), 1.27 one release later. Choosing the newest major delays the next forced upgrade.

How it is selected (doc `https://go.dev/doc/toolchain`, read 2026-11-11): with `GOTOOLCHAIN=auto` the PC's
go1.22.2 reads the `go`/`toolchain` lines and downloads `golang.org/toolchain@v0.0.1-go1.27.4.linux-amd64` as a
module; "toolchain downloads can be proxied by setting GOPROXY and have their checksums checked by the Go checksum
database". The gate does not rely on `auto`: `tools/lib.sh` reads the `toolchain` line from `go.mod` and exports
`GOTOOLCHAIN=<that value>` exactly, then checks `go env GOVERSION` equals it (refuses otherwise). Reason: under
`auto`, a newer local Go would be used instead, and `go install pkg@version` follows the *installed module's* go
line, not ours, so analysers would silently be built with another Go.

Seen on the PC (scratch module outside the repository, 2026-11-11):
- `go version` in a module with the lines above: downloaded go1.27.4 in 15 s, printed `go1.27.4 linux/amd64`, rc 0.
- `GOTOOLCHAIN=local` with go1.22.2: `go: go.mod requires go >= 1.27.0 (running go 1.22.2; GOTOOLCHAIN=local)`,
  i.e. the old toolchain cannot build the module by mistake.
- `govulncheck -test ./...` (v1.9.0 built with go1.27.4) on a module using `iter.Seq` and range-over-int:
  "No vulnerabilities found.", rc 0; `govulncheck -mode binary` on a go1.27.4 binary: rc 0.

### 3.2 Module path: `nmb`

Quality Bar 8 (roadmap 595) keeps account names out of the code base, so `github.com/<account>/...` is not used.
Proposed: the dotless path **`nmb`** (imports read `nmb/internal/buildinfo`). What the Go reference says
(`https://go.dev/ref/mod`, *Module paths*, read 2026-11-11): "A module that will never be fetched as a dependency of
any other module may use any valid package path ... The Go standard library uses package paths that do not contain
a dot in the first path element, and the go command does not attempt to resolve such paths from network servers.
The paths example and test are reserved for users".

What it costs:
1. Nobody can `go get` / `go install nmb/cmd/nmbd@vX` from the internet; users get built binaries and packages
   anyway (P-11), and every package is `internal/` or `cmd/`, so no outside import is intended.
2. A theoretical collision if the standard library ever adds a top-level package `nmb`; then a one-line rename of
   the module path (mechanical `sed` over imports). `example/nmb` would avoid even that, but reads like a tutorial.
3. pkg.go.dev will not index it (not wanted).
4. Tools: checked on the PC with module `nmb`: `staticcheck` rc 0, `govulncheck` rc 0, `go vet` rc 0, the gosec
   analyser rc 0 (clean) and rc 3 with planted findings, cross builds of all five targets rc 0.

### 3.3 Analysers: pinned, built with the fixed toolchain, outside the repository

The binaries in `~/go/bin` were built with go1.22.2 (seen with `go version -m`) and are not used: an analyser
type-checks with the `go/types` it was compiled with and cannot read code for a newer Go.

| Tool | Module and version (latest on proxy.golang.org, 2026-11-11) | Licence (file seen in module cache) | How installed | Seen on PC |
| :--- | :--- | :--- | :--- | :--- |
| staticcheck | `honnef.co/go/tools` v0.8.2 (tag 2026.2.2) | MIT (`LICENSE`, plus `LICENSE-THIRD-PARTY`) | `go install honnef.co/go/tools/cmd/staticcheck@v0.8.2` | built 84 s, peak 310 MB, rc 0 |
| govulncheck | `golang.org/x/vuln` v1.9.0 | BSD-3-Clause | `go install golang.org/x/vuln/cmd/govulncheck@v1.9.0` | built 14 s, 231 MB, rc 0 |
| gocyclo | `github.com/fzipp/gocyclo` v0.6.0 | BSD-3-Clause | `go install github.com/fzipp/gocyclo/cmd/gocyclo@v0.6.0` | built 1 s, rc 0 |
| gosec rules | `github.com/securego/gosec/v2` v2.30.0 through its `goanalysis` package | Apache-2.0 (`LICENSE.txt`) | own 10-line driver module `tools/gosecvet/` (below) | built 9 s, 220 MB, rc 0 |

**gosec, the finding:** the `gosec` command of v2.23.0 to v2.30.0 imports its `autofix` package, which pulls in
three large AI vendor SDKs (seen in the published `go.mod` files of each version). On this PC
`go install .../cmd/gosec@v2.30.0` swapped for more than 15 minutes and the compiler process for one SDK package
was killed (`signal: killed`, 1.0-1.1 GB resident; kernel OOM messages present), so the install failed. v2.22.0 (the
last without them) builds with go1.27.4 but fails on our code: `internal error: package "fmt" without types was
imported from "command-line-arguments"`, rc 1. **Decision:** use gosec's own official go/analysis entry point,
`github.com/securego/gosec/v2/goanalysis.Analyzer`, through a driver:

```go
// tools/gosecvet/main.go (whole program; a separate module so its dependencies stay out of the product go.mod)
package main

import (
	"github.com/securego/gosec/v2/goanalysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

func main() { singlechecker.Main(goanalysis.Analyzer) }
```

`tools/gosecvet/go.mod`: `module nmb/tools/gosecvet`, `go 1.27.0`, `toolchain go1.27.4`, requires
`github.com/securego/gosec/v2 v2.30.0` and `golang.org/x/tools v0.52.0` (the same version gosec v2.30.0's own
`go.mod` requires); `go mod tidy` adds `github.com/ccojocar/zxcvbn-go v1.0.4` (MIT), `golang.org/x/mod v0.42.0`,
`golang.org/x/sync v0.24.0` (BSD-3-Clause). `go list -deps` of the driver: 0 packages of the AI SDKs. Trial: on a
clean module rc 0; with a planted `exec.Command("sh","-c",arg)` and `os.ReadFile(p)` it reported `G204` and `G304`
and exited **3** (singlechecker: 3 = diagnostics found). Same rules and version as the command; what the driver
lacks is the command's report formats and its AI fix suggestions (not wanted). `go.sum` of the driver is committed,
so its whole dependency set is pinned by hash.

staticcheck, govulncheck and gocyclo are installed with `go install path@version` (each with its own released,
tested dependency set; module zips verified by `sum.golang.org`). They are deliberately **not** put together in one
`tool`-directive module: minimal version selection would build staticcheck against gosec's newer `x/tools`.

Where they go: `${NMB_TOOLS_DIR:-$HOME/.cache/nmb/gate-tools}/<toolchain>/<tool>@<version>/<tool>` (outside every
repository, shared by all worktrees, versioned names, never committed). `tools/prepare.sh` skips a tool when
`go version -m` of the existing binary shows the expected toolchain and module version, and otherwise rebuilds it;
after installing, it checks exactly that and fails otherwise. Versions come from one place: the gate-tool rows of
`docs/DEPENDENCIES.md` (section 4.6), which the script reads; there is no second copy in the script.

Complexity checker: `gocyclo -over 15` (cyclomatic complexity above 15 fails). The plans name `gocyclo` but no
number; 15 is the analyst's choice (the rules ask for one job per unit and small functions, which the length and
nesting limits already bound). gocognit was looked at (v1.3.0, MIT) and left out: one complexity tool is enough.

### 4.2 `internal/buildinfo` and `cmd/nmbd` (Phase 0 stub)

`buildinfo` reads `runtime/debug.ReadBuildInfo()` through an injected function (tests pass fakes) and returns a
struct: main module version, Go version, GOOS, GOARCH, GOARM or GOMIPS when set, `vcs.revision`, `vcs.time`,
`vcs.modified`. No version number is invented: since Go 1.24 `go build` stamps the main module version from git
(seen on the PC with go1.27.4 in a scratch repository: `mod nmb v0.0.0-20261111050751-82cd6994c9e6`, plus
`vcs.revision`, `vcs.time`, `vcs.modified=false`). A field the build did not record is reported as "not recorded",
never as a default. The changelog's first version `0.1.0` (roadmap 703) comes from a git tag at release.

`nmbd` (no daemon yet, nothing usable, said in its usage text):
- `nmbd --help` or `-h`: usage to stdout, exit 0, nothing else (no file, no socket, no environment change).
- `nmbd --version`: the buildinfo lines to stdout, exit 0.
- no argument, an unknown option or extra arguments: usage to stderr, exit 2.
- Parsing with the standard `flag` package on a `flag.FlagSet` built per call (no globals), output writers passed
  in, so `main` is only `os.Exit(run(os.Args[1:], os.Stdout, os.Stderr))`.
- `docs/cli/nmbd.md` holds the usage text in one fenced block; a test in `cmd/nmbd` reads
  `../../docs/cli/nmbd.md` and compares that block with the `--help` output byte for byte (6B.7: they can never
  disagree). The entry also gives exit codes (0, 2), "changes nothing", "needs no root", and an example.
- Multi-call names (roadmap 494, P-10) are not part of F-00.

### 4.3 Shell scripts (all bash, `set -euo pipefail`, shellcheck clean)

Common rules, enforced in review and by `gate-selftest.sh`:
- A step's status is taken from the command itself: `if cmd >"$log" 2>&1; then rc=0; else rc=$?; fi`. Output is
  shown afterwards from the log file (`tail` on the file, never in the pipe of the status). No `| tail`, `| tee`,
  `| grep` in front of a status; where a pipe is unavoidable, `PIPESTATUS` is checked element by element.
- Refuse to run as root (`id -u` is 0) with exit 2 (fault KF-0001: tests as root overwrote real settings).
- Refuse when `GOSUMDB=off`, or `GONOSUMDB`, `GONOSUMCHECK`, `GOINSECURE`, `GOPRIVATE` or `GOFLAGS` with
  `-insecure` are set (the checksum database is what makes downloads trustworthy).
- File lists come from `git ls-files -z` (NUL-separated), never from word-splitting; every variable quoted; `--`
  before paths; temp folders by `mktemp -d` and removed by `trap`.
- Environment knobs, each validated: `NMB_GATE_JOBS` (integer 1-4, default 2: Go `-p` and fuzz `-parallel`),
  `NMB_FUZZTIME` (`^[0-9]+[sm]$`, default `30s`), `NMB_TOOLS_DIR` (absolute path), `NMB_PRIVATE_VALUES` (4.5).
- Results go to `build/gate/<UTC time>/` (ignored by `/build/`): one log per step, `summary.tsv` (step, where it
  ran, rc, seconds), `sizes.tsv`, `tools.txt` (`go version -m` of every analyser).

#### 4.3.1 Test runs

Race detector requirement (`https://go.dev/doc/articles/race_detector`, read 2026-11-11): "The race detector
requires cgo to be enabled, and on non-Darwin systems requires an installed C compiler." Seen on the PC with
go1.27.4: `CGO_ENABLED=0 go test -race` -> "go: -race requires cgo", rc 2; `CGO_ENABLED=1 go test -race` -> ok,
rc 0 (gcc 13.3.0 present). So the race run is the **only** place with cgo; it builds test binaries only, never a
shipped binary, and a second amd64 run uses `CGO_ENABLED=0`.

| Run | Where | Settings |
| :--- | :--- | :--- |
| A | PC amd64 | `CGO_ENABLED=1 go test -race -count=1 ./...`, `TZ=UTC` |
| B | PC amd64 | `CGO_ENABLED=0 go test -count=1 -shuffle=on ./...`, `TZ=Pacific/Chatham` (+13:45, with DST) |
| C, D | QEMU user mode arm64 | test binaries from `CGO_ENABLED=0 GOARCH=arm64 go test -c -o <dir>/<pkgpath-with-dashes>.test <pkg>`, one package at a time (package names repeat: `main`); each binary run as `qemu-aarch64-static <bin> -test.count=1` from its package's source folder; C with `TZ=UTC`, D with `TZ=Pacific/Chatham -test.shuffle=on` |
| E, F | QEMU user mode arm v7 | the same with `GOARCH=arm GOARM=7` and `qemu-arm-static` |
| G | compile only | `go test -c` for mips and mipsle softfloat (catches test code that does not build on 32-bit big/little endian) |

For every run: `-count=1` (no test cache), `HOME` and `TMPDIR` set to fresh empty temp folders (Go's
`GOCACHE`, `GOMODCACHE`, `GOPATH` are read first and exported explicitly), and `git status --porcelain` is the same
before and after (a test that writes into the repository fails the step). Packages without test files are listed
as "no tests" and skipped for `-c`.

Offline (seen on the PC): `unshare -rn` works without root (rc 0), but inside it the process is uid 0 of the user
namespace, so tests would see "root". The wrapper therefore nests a second user namespace mapped back to the real
user:

```sh
unshare -rn sh -c 'ip link set lo up && exec unshare --user --map-user="$1" --map-group="$2" -- "$@"' ...
```

Seen on the PC: inside, `id -u` printed the real uid, `CapEff` 0000000000000000, `lo` up with 127.0.0.1, name
resolution failed (no network), and `GOPROXY=off go version` printed go1.27.4 (toolchain from the module cache).
`unshare --map-current-user -n` alone cannot bring `lo` up ("RTNETLINK answers: Operation not permitted"), and
loopback is needed by `httptest` servers in later packages. `ip` is looked up in `PATH`, `/usr/sbin`, `/sbin`
(roadmap 686). If the namespace cannot be made, the step still runs but `summary.tsv` and the final output say
`NOT OFFLINE` for it (never silently). Unprivileged ICMP is off in a new namespace (`ping` to 127.0.0.1 failed);
tests needing ICMP get fakes from F-06.

Not possible with these means and said in the result: shifting the clock (Go binaries are static, `LD_PRELOAD`
tools do not apply); wall/monotonic clock independence is a test-design rule (F-06 fake clock), not a gate step.

Trial (scratch): arm64 test binary under `qemu-aarch64-static` rc 0; arm v7 under `qemu-arm-static` rc 0; mips and
mipsle builds rc 0 (`file`: "ELF 32-bit MSB ... MIPS32" and "LSB").

#### 4.3.2 Fuzzing

Doc `https://go.dev/doc/security/fuzz/` (read 2026-11-11): `-fuzz` takes "a regex matching a single fuzz test"; the
generated corpus lives in `$GOCACHE/fuzz`; failing inputs are written to `testdata/fuzz/<Name>/` of the package.
`fuzz.sh`: for each package (`go list ./...`) list `go test -list '^Fuzz' -run '^$' <pkg>`; for each name run
`go test -run '^$' -fuzz "^<Name>$" -fuzztime "$NMB_FUZZTIME" -parallel "$NMB_GATE_JOBS" <pkg>` on amd64 inside
`offline`. A failure fails the step and leaves the new `testdata/fuzz/<Name>/<hash>` file in the worktree for the
implementer to commit as a regression seed (gate skill 4). The step prints how many targets ran (0 is printed,
not hidden). Seen on the PC: a 5 s fuzz run with `-parallel 2`, rc 0, peak 264 MB.

Fuzz targets F-00 must have: `FuzzScan` (privscan's line scanner), `FuzzParseDependencies` (depcheck's table
parser), `FuzzCheckSource` (cleancode on arbitrary bytes: never panics, errors are returned), `FuzzRun` (nmbd's
argument handling: never panics, exit code is 0 or 2, never writes a file).

### 4.4 `tools/cleancode` (go/ast checker)

Input: the Go files of `git ls-files '*.go'` (paths as arguments). Rules (roadmap 738-740):
- **Function length:** lines strictly between the body's `{` and `}` of a `FuncDecl` (and of each top-level
  function literal assigned at package level), all physical lines counted; more than 50 fails.
- **File length:** physical lines; more than 500 fails. Also applied to `tools/*.sh`.
- **Stated reason:** "A longer one needs a stated reason in review": a doc comment line
  `//nmb:allow-long <reason>` on the function (or `//nmb:allow-long-file <reason>` before `package`) turns the
  failure into a listed exception; an empty reason is a failure; every exception is printed in the gate output so
  the verifier sees it.
- **Nesting:** the function body is level 0; `if`, `for`, `range`, `switch`, type switch, `select`, a bare block
  and a function literal each open one level; `else if` chains stay on the level of their `if`; `case` and
  `default` clauses do not add one. Level 4 anywhere fails, with no exception directive (the rule is "at most
  three").
- Output: `path:line: rule: value (limit N)`; exit 1 on a violation, 2 on a read or parse error (a file that cannot
  be parsed is never passed).

### 4.5 `tools/privscan` (personal data and secrets)

Modes: `tree` (files given by `scan.sh`), `dist` (files under `dist/`, scanned as bytes), `history` (every blob
reachable from all refs via `git rev-list --objects --all` and `git cat-file --batch`, plus every commit message).
Files are read with a `bufio.Reader` (no 64 KiB line limit: a long line is scanned, never skipped); a file over
256 MiB is an error, not a pass. Regular expressions are Go's RE2 (linear time). Exit 0 clean, 1 hits, 2 error.

Rules (a hit unless allowed):

| Category | Detects | Allowed |
| :--- | :--- | :--- |
| `email` | `<local part>` `@` `<domain with a letters-only top-level label>`; `path@v<digit>...` (Go module queries such as `tool@v1.2.3`) is not an address | domain `example.com`, `example.net`, `example.org` or a subdomain; TLDs `.example`, `.invalid`, `.test`, `.localhost` (RFC 2606, RFC 6761) |
| `ipv4` | dotted quads parsed with `net/netip`, not part of a longer dotted number | 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24 (RFC 5737); 10/8, 172.16/12, 192.168/16; 127/8; 169.254/16; 0/8; 192.0.0.0/24; 198.18.0.0/15; 224/4 and 240/4 including 255.255.255.255. **100.64.0.0/10 (RFC 6598) is a hit** (tailnet and carrier addresses live there; see question Q3) |
| `ipv6` | tokens of hex, `:` and `.` with `::` or seven colons, parsed with `net/netip` | 2001:db8::/32 (RFC 3849), 3fff::/20 (RFC 9637), `::`, `::1`, fc00::/7, ff00::/8, 64:ff9b::/96, IPv4-mapped forms of allowed IPv4; fe80::/10 **unless** its interface id is EUI-64 (`ff:fe` in the middle) from a universally administered MAC |
| `mac` | `xx:xx:xx:xx:xx:xx`, `xx-xx-..`, `xxxx.xxxx.xxxx` | locally administered (second-lowest bit of the first octet set, e.g. `02:00:00:..`), multicast (lowest bit set), all zeros |
| `key` | `-----BEGIN ... PRIVATE KEY-----`; OpenSSH public keys (`ssh-ed25519`, `ssh-rsa`, `ecdsa-sha2-*` followed by base64); `AGE-SECRET-KEY-1`; GitHub `ghp_/gho_/ghu_/ghs_/ghr_` + 36 and `github_pat_`; GitLab `glpat-`; Slack `xox[abprs]-`; AWS `AKIA` + 16; Google `AIza` + 35; Telegram bot token `\d{8,10}:[A-Za-z0-9_-]{35}`; Tailscale `tskey-`; `sk-` API keys; JWTs; WireGuard `PrivateKey/PresharedKey/PublicKey = <44 base64>`; `password/passwd/secret/token/api_key` assignments with a value of 12+ characters and entropy of at least 3.5 bits per character | placeholders `<...>`, `${...}`, `__KEEP_CURRENT__`, values containing `example`; `go.sum` `h1:` hashes do not match any rule |
| `path` | `/home/<x>/`, `/Users/<x>/`, `/mnt/<drive>/Users/<x>/`, `<drive>:\Users\<x>`, `<drive>:/Users/<x>` | `<x>` = `nmb` (the service user, roadmap 685), `Public`, `Default`, `Shared`, or a placeholder (`<user>`, `<name>`, `$USER`, `%USERNAME%`) |

- **Allow list in the repository:** `tools/privscan/allow.txt`, lines `<category> <exact value> <reason>`; an
  entry allows only that exact value; an entry without a reason is an error. F-00 ships its header and one entry:
  `ipv4 100.64.0.0 the shared address space named as a range (RFC 6598) in this brief and in privscan's docs`.
  Every entry added later is reviewed by that package's verifier (public resolver addresses for M-12 will need it).
- **Private list:** path from `NMB_PRIVATE_VALUES`; refused (exit 2) if it resolves inside the repository, is not a
  regular file, or has a value shorter than 4 characters; values are never printed or written anywhere: a hit says
  `private value #<line number>`. Unset: the scan passes the other rules and prints `private list: not used`;
  `--require-private` (used by the orchestrator before a push) makes it an error.
- **Masked output:** a hit prints `path:line:col: category: <first 2 characters>…(<length>)`, never the full value,
  so the gate logs do not repeat a secret.
- **Binaries:** `dist` mode needs `-trimpath`: seen on the PC, a go1.27.4 hello-world built without it held the
  build machine's home path twice; with `-trimpath -ldflags='-s -w'` zero times. A stripped hello-world held no
  e-mail-, IPv4- or MAC-like string.
- **History mode and commit identities:** `history` also lists the distinct author and committer addresses of all
  commits and fails on any that is not a GitHub noreply form, unless the address is in the private list as accepted
  (question Q1). It is run by the orchestrator before the first push, not by `gate.sh` per package.
