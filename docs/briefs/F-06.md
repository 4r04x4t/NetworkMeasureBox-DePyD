### 3.2 What the test bed does

- **Gives every package fixed inputs for time, files, processes, the network and the outside world**, as Go
  implementations of F-04's interfaces, so a unit test touches nothing of the machine (REQ-RM-1253, REQ-TS-0172).
- **Runs network tests in throwaway namespaces** joined by virtual cables, as the PC user, without root

## 4. Interfaces used (F-04) and what is needed from F-04

F-04's contracts are briefed in F-04a..f (section 1; not yet accepted). F-06 implements fakes **of** them, under
F-04's names, and adds no interface of its own to the product. Revision 1 of this brief was written before those
briefs existed and proposed its own `Clock` and `Paths` shapes; this revision aligns with F-04 and keeps only the
timer part as a proposal (4.2).

### 4.1 Clock and path facts F-06's fakes implement

- **Time** (F-04c 3.1 point 2): stored and exchanged times are UTC milliseconds (`ts`); durations and ordering inside
  one boot come from `mono_ms`, milliseconds since boot on `CLOCK_BOOTTIME`, together with the boot id (`boot`, the
  first 8 hex digits of `/proc/sys/kernel/random/boot_id`). So the monotonic reading is comparable across processes
  within one boot.
- **Clock facts** (F-04d 4.9.1, part of `System`, 4.16): `Monotonic()`, `Boottime()`, `BootID()`, `ClockSync()`
  (`{synced, max_error_us?, source?}`), `ClockSteps()` (a stream; steps are jumps of `CLOCK_REALTIME` minus
  `CLOCK_BOOTTIME` over 1 s, for F-04c's `clock_step` event).
- **Paths** (F-04d 4.9.2): `Layout()` returns the path table of F-04c 3.9.1 (roots `RUN`, `STATE`, `PERSIST`, `CACHE`,
  `LOG`, plus `CONFIG` and the boot partitions), with no fallback location (KF-0290); `Mounts()`, `Statvfs()`, and thin
  wrappers for directory handles (`os.Root`), `O_NOFOLLOW`, `flock`, `fchown`/`fchmod` and directory `fsync`, "so the
  fakes can fail a chosen call".

`clock.FakeClock` implements exactly these clock facts (5.1), and `host.Layout(t)` implements `Layout()` with every
root under the test's own folder (5.2.1). No separate `Paths` contract is proposed any more.

### 4.2 What F-06 still proposes to F-04 (timers)

None of F-04a..f defines timers or sleeps: F-04d 4.9.1 gives readings only. Every component that waits needs timers,
tickers, cancellable sleeps and deadlines that a fake can drive. Proposed for F-04d's `System` or for C-05's
"monotonic time helpers" (REQ-RM-1056, work plan 124), question Q1; F-06 fakes whatever is fixed:

```go
// Proposal only (not defined by F-06). Mono is CLOCK_BOOTTIME since boot in nanoseconds: the clock of F-04c's
// mono_ms (mono_ms = Mono / 1e6), comparable across processes within one boot (same BootID), never a date.
type Mono int64

type Timers interface {
	NewTimer(d time.Duration) Timer                                                       // fires after d of boottime
	NewTicker(d time.Duration) Ticker
	Sleep(ctx context.Context, d time.Duration) error                                     // ctx.Err() when cancelled
	WithTimeout(ctx context.Context, d time.Duration) (context.Context, context.CancelFunc) // deadline on this clock
}
```

Why a distinct `Mono` type and not `time.Time`: a `time.Time` made by a fake carries no monotonic reading, so `t.Sub`
silently falls back to wall time; a distinct type makes "duration from the wall clock" a compile error. Network I/O:
product code bounds a socket operation with `WithTimeout` of this clock (the cancel closes the connection), never with
`conn.SetDeadline(time.Now().Add(d))`; under the fake clock a test then advances time and the I/O is cut. How tests
use real deadlines is in 5.8.

### 5.1 Fake clock

5.1.1 `FakeClock` implements the clock facts of F-04d 4.9.1 (`Monotonic()`, `Boottime()`, `BootID()`,
`ClockSync()`, `ClockSteps()`, section 4.1) and the timer proposal of 4.2. It holds a boottime instant (`Mono`,
nanoseconds since boot, so `mono_ms` of F-04c 3.1 is `Mono/1e6`), a boot id, and a wall instant with a
`*time.Location`. It never sleeps and never reads the real clock. In the fake, `Monotonic()` and `Boottime()` are the
same reading (no suspend is simulated).

5.1.2 Operations (each one locks one mutex; timers are a min-heap ordered by due `Mono`, ties by creation order):

| Call | Effect |
| :--- | :--- |
| `New(start time.Time, loc *time.Location, opts...)` | wall = `start`; boottime = the default uptime 3 h 7 min 11 s (a non-trivial value, so code that treats 0 as "never" is caught); boot id = `reserved.BootID(1)`; `WithUptime(d)` sets the uptime (catalogue 7: `WithUptime(30*time.Second)`) |
| `NewBoot(uptime)` | a reboot: a new boot id (`reserved.BootID(n+1)`), boottime back to `uptime`, timers dropped; wall kept unless stepped |
| `Advance(d)` | moves mono and wall by `d`; fires every timer due on the way, in order, each at its own instant (wall and mono at the moment of firing equal the due time) |
| `StepWall(d)` | wall only, forward or backward (NTP step, the WSL +1 h jump of 2026-11-10, a battery-less Pi booting in 1970); timers do not fire; a step of more than 1 s is sent on `ClockSteps()` as F-04d 4.9.1 detects it |
| `SetSync(synced, maxErrorUs)` | the answer of `ClockSync()` |
| `SetLocation(loc)` | zone change (first-start setup, QB 9) without moving the instant |
| `BlockUntilWaiters(n, limit)` | waits (real time, bounded by `limit`, default 5 s) until `n` goroutines are blocked on this clock: the only real-time wait, so a test does not race a goroutine that has not reached its `Sleep` yet |
| `Waiters()`, `Pending()` | for assertions |

5.1.3 Time zones: `testbed/clock` imports `time/tzdata` (embedded zone database), so test zones never depend on the
host's `/usr/share/zoneinfo`. Fixtures: `UTC`, `Pacific/Chatham` (+12:45/+13:45, the zone of F-00's run B),
`America/St_Johns` (-3:30, DST), `Asia/Kathmandu` (+5:45), `Australia/Lord_Howe` (30-minute DST),
`Europe/Berlin` (DST gap and overlap at 02:00/03:00), and helpers `DSTGap(loc, year)`, `DSTOverlap(loc, year)` that
return instants found by scanning the zone (no hard-coded dates). Whether `nmbd` itself embeds tzdata is C-10's and
P-11's decision, not this one.

5.1.4 Boot-relative time: `FakeClock` boottime is "since boot" by contract (F-04c 3.1) and starts at the default
uptime unless `WithUptime` says otherwise, and `fakesys` serves `/proc/uptime` from the fake clock, so "the first
minute after boot" (catalogue 7) is a test input (`WithUptime(30*time.Second)`).
For a program that is not ours (an engine binary, a tool) the same is done for real in the netns tier with a
**time namespace**: `CLONE_NEWTIME` with negative `monotonic` and `boottime` offsets written to
`/proc/self/timens_offsets` before the first child starts; checked on this PC (8.1: a static Go binary saw
`CLOCK_MONOTONIC` = 30 s). A time namespace cannot move `CLOCK_REALTIME` (`time_namespaces(7)`), so wall steps for
foreign programs are not possible without root and are not offered.

5.1.5 `tools/clockjump`: the dev-setup check of REQ-DV-0008, correctly: sample wall and monotonic every 10 ms for
30 s **of monotonic time measured from a fixed start**, count steps where the two differ by more than 0.5 s, print
`clock jumps in 30 s: N` and exit 1 when N > 0. The Python document's loop reassigns the variable it uses as its end
time, so it never ends (8.1, Q3). The gate prints its result in `environment.tsv` (integrator change, 5.10).

5.1.6 Real `Clock` conformance (with C-05): a suite `conformance.Clock(t, factory)` checks ordering, timer firing,
cancel, ticker drop semantics, `Sleep` cancel; it runs on the fake (fast) and on C-05's real clock (short real
durations, under 1 s total).

### 5.2 Host isolation: paths, writes, logs, environment, capability profiles

5.2.1 `host.Layout(t)` returns F-04d 4.9.2's `Layout()` with every root of F-04c 3.9.1 (`RUN`, `STATE`, `PERSIST`,
`CACHE`, `LOG`, `CONFIG`, the boot partition) under `t.TempDir()` (`RUN` under a short directory, see 5.6.5 on the
108-byte socket limit). There is no fallback to a system path; asking for an unknown root fails the test.

5.2.2 Write guard (KF-0290, REQ-RM-1058, REQ-TS-0003). F-00's `nmb_hermetic` (F-00:`tools/lib.sh:200-208`) gives
one fresh `HOME`, `TMPDIR` and `GOTMPDIR` to a whole `go test -p $NMB_GATE_JOBS ./...` (default 2 jobs), so test
binaries of different packages run at the same time against the same folders, and `t.Parallel` tests inside one
binary do too. A guard that snapshots those shared folders would blame one test for another's files (and Go 1.27.4's
`t.TempDir()` is created under `GOTMPDIR` when it is set, else under `os.TempDir()`: `testing.go` 1575, 1615, so
"outside `t.TempDir()`" cannot be told apart reliably). The guard therefore works at three levels, each exact:

1. **Per test binary**: `host.Main(m)`, called from the package's `TestMain`, creates a private folder under the
   inherited `TMPDIR` with its own `home`, `tmp`, `gotmp` and `xdg` folders, sets `HOME`, `TMPDIR`, `GOTMPDIR` and
   `XDG_CONFIG_HOME`/`XDG_CACHE_HOME`/`XDG_DATA_HOME` to them (before any test runs, so no goroutine of a test races
   it), runs `m.Run()`, then checks once that `home`, `tmp` and `gotmp` are empty (every `t.TempDir()` has been removed
   by then), prints what was left with sizes, removes the private folder and exits non-zero when anything was left.
   `hermeticcheck` (5.8) fails a test package under `internal/` or `cmd/` without such a `TestMain`; F-00's `tools/`
   packages, written before the test bed, are on its allowed list with that reason.
2. **Per test, for tests that are not parallel**: `host.Guard(t)` gives the test its own fresh `HOME` and `TMPDIR`
   through `t.Setenv` and fails the test in `t.Cleanup` when either is not empty. Go's `t.Setenv` panics in a test that
   calls `t.Parallel` (and in its subtests), so the guard is structurally limited to non-parallel tests, during which
   no parallel test of the same binary runs; a parallel test is covered by level 1 only. The cleanup order is safe: a
   `t.TempDir()` made after the guard is removed before the guard's check (cleanups run last-in first-out).
3. **Per run**: the gate fails a run when the shared `HOME`, `TMPDIR` or `GOTMPDIR` of `nmb_hermetic` is not empty
   afterwards (integrator change 5.10 point 2), which catches test binaries that do not use `host.Main` (F-00's).

5.2.3 Log guard: `host.Secrets(t)` makes obviously fake secrets (`reserved.Token(n)`, e.g. `test-token-0000…`) and
fails the test if one of them appears in captured logs, events, bundles or error strings (REQ-CT-0017; the masking
itself is C-04's).

5.2.4 Capability profiles (REQ-WP-0154): `fakesys.Profile` = file tree + tool table + init system, one per column of
F-04d 4.12's capability table (F-04d 4.15: "one fixture per column"), starting with the bases recorded so far:
`openwrt-25.12` (BusyBox `ip` without `-br`, procd, `udhcpc`, no `iw`/`hostapd`, `nft` 1.1.6: I-01 §7), `debian-13`
(full iproute2 6.15, systemd 257, `dhcpcd-base`, `nft` 1.1.3: I-06 §7), and the edge cases "tool outside `PATH`"
(roadmap 686), "tool missing", "other init", plus the edge devices of F-04d 4.15 (`rndis_host` tether, `cdc_ether`
dongle, a PCI NIC without driver). Each profile names the record and section it came from; a column F-04d marks "nd"
gets no invented values. The same package serves F-04a's fixtures: mountinfo `BootFAT`/`NoBoot`/`BootFATReadOnly`,
passwd and group tables for the user lookup, watchdog and journal/kmsg readers (F-04c), and `FailFS` (fails the n-th
call of a chosen file operation of F-04d 4.9.2 with a chosen errno, or every write after N bytes).

5.2.5 Environment guard: `host.Env(t)` clears `NMB_*` and proxy variables for the test and fails when product code
reads an environment variable the test did not set (through F-04's config, never `os.Getenv` in components:
`hermeticcheck`).

5.2.6 `host.ReExec(t, role, fn)`: runs `fn` in a child process, the test binary itself re-executed as
`<binary> -test.run '^<TestName>$' -test.count=1` with a role variable (the mechanism of 5.4.1 without namespaces).
It serves F-04a's T-02, F-04d's `fakesup` roles (stays, exits with n, ignores SIGTERM, writes to stdout/stderr) and
F-04b's "killed during a snapshot": `KillAt(point)` makes the child report named points over a pipe, and the parent
sends SIGKILL when the chosen point is reached (no timing guess). The child's output and exit status are returned.

5.2.7 File-access recorder (F-04c T-SPEC-2): `fakesys.Recorder` wraps F-04d 4.9.2's file operations and records
every open, create and rename with root, component and mode; `host.RootsAudit(t, layout)` lists, after a whole-binary
run with every root a fresh folder, each file created, and compares it with `spec/files/registry.json`. Limit: reads
by a separate binary are not recorded (fanotify needs `CAP_SYS_ADMIN` in the initial user namespace).

### 5.3 Fakes of F-04's interfaces and the recorded command runner

5.3.1 Each fake carries F-04's name (4.3: `fakenet`, `fakewifi`, `fakectrl`, `fakefw`, `fakeinit`, `fakesup`,
`fakesys`, `fakepriv`, `fakestore`) and is a type with a compile-time assertion `var _ <contract>.<Iface> =
(*Fake)(nil)` (KF-0074: a changed interface breaks the build of the fake, not a test at run time). Every fake can
inject each error code of F-04d 4.0.5 (`Inject(op, code)`, F-04d R19).

5.3.2 Conformance suites (`internal/testbed/conformance`): for each F-04 interface a function
`<Iface>(t, impl)` with the behaviours both the fake and the real implementation must show (errors as typed values,
missing tool, empty results, ordering). The real implementation's package runs the same suite in the netns or guest
tier. A fake that passes the suite cannot return an invented shape (REQ-TS-0205, REQ-CT-0013).

5.3.3 `fakeexec`: a `Runner` (F-04's system-tool contract) whose responses are keyed by the exact argv; each
response file holds stdout, stderr, exit code, duration and a `source:` line (the record and command it was captured
from, for example "I-01 §7, guest `nft --version`"). An unknown argv fails the test (never a default success). Built-in
cases: missing binary, not executable, timeout, killed, output larger than the caller's limit.

5.3.4 Wi-Fi fake: a regdomain change is recorded, and a test that did not declare `ExpectRegdomainSet(cc)` fails at
cleanup (REQ-CL-0230, KF-0051).

### 5.4 Namespace tier: user and network namespaces with virtual cables

5.4.1 Entry: `netns.Run(t, func(tb *netns.Bed), opts...)`. If the test is not yet inside a test-bed namespace, it
re-executes the test binary as `<binary> -test.run '^<TestName>$' -test.count=1` with `SysProcAttr{Cloneflags:
CLONE_NEWUSER|CLONE_NEWNET|CLONE_NEWNS, UidMappings: 0→caller uid, GidMappings: 0→caller gid}` and a marker
variable, and reports the child's result as the test's. The mount namespace lets the bed mount a fresh `sysfs` (so
`/sys/class/net` shows the bed's own links) and `host.SmallFS(t, size)` mount a `tmpfs` of a set size (F-04b
T-PRUNE-2; checked: a 1 MiB tmpfs in `unshare -rm` was full at 1 MiB, 8.1).

**More than one user** (F-04c T-IPC-2): with `netns.Users(n)` the child is started with `CLONE_NEWUSER` but without
Go's mappings and waits on a pipe; the parent runs `newuidmap <pid> 0 <uid> 1 1 <first subordinate id> 65536` and the
same with `newgidmap` (ranges read from `/etc/subuid` and `/etc/subgid` for the user), then releases it. Inside,
`tb.AsUser(uid, fn)` runs `fn` in a child with `SysProcAttr.Credential` set to that uid and gid. Checked:
`unshare --map-auto --map-root-user -n -m` gave the maps `0 <uid> 1` and `1 <subordinate start> 65536`, and
`setpriv --reuid=1001 --regid=1001` ran a command as uid 1001 in the namespace (8.1). `newuidmap`/`newgidmap` are
the shadow suite's set-uid helpers (`uidmap` package): the only host programs the namespace tier runs, each only to
write the map of its own child; without them, or without a subordinate range, a test that needs `Users` is "not run:
no subordinate ids" (never run with one user instead). Inside, the process is uid 0 **only in its own user namespace**
(capabilities over that namespace and its children, none over the host). Checked on this PC (8.1): a Go child made
this way saw uid 0, opened NETLINK_ROUTE and could `unshare(CLONE_NEWNET)` again; inside F-00's offline wrapper
(mapped back, no capabilities) a nested user+net namespace still works.

Fail closed: before creating anything, the bed reads `/proc/self/uid_map`; if it is the initial namespace's map
(`0 0 4294967295`) it refuses (`TestRefusesInitialUserNamespace`), so even when started by real root it can never
change real interfaces. It also refuses when the real uid outside is 0 (KF-0001).

5.4.2 Nodes and cables: a node is a network namespace held by an open file descriptor (made on a locked OS thread
with `unshare(CLONE_NEWNET)`, fd from `/proc/thread-self/ns/net`). Code runs "in" a node with `tb.Node("lan").Do(fn)`
(locked thread, `setns`, back). A fake server runs in a node in its own goroutine on its own locked thread, or as a
child process started inside the node for programs that are not ours (QB 6B.5 third-party engines).

5.4.7 **Box mode** (REQ-RM-1353, roadmap 6B.5 "Sandboxed self-test and update", `DEPYTHONIZATION_ROADMAP.md@ad3758c:879`:
"Tests that touch the network (firewall, DNS, DHCP, routing) run in throwaway network namespaces with virtual cables,
never on the real interfaces"). Revision 1 of this brief kept the namespace tier off the box; that contradicted 6B.5
and is withdrawn. The tier runs in P-02's sandboxed self-test and update run on the box, under these rules:

- **Never root, never the initial namespace**: P-02's run is an unprivileged user (memory rule; KF-0001); the bed makes
  its own user namespace and refuses the initial one and a real uid 0 exactly as on the PC (5.4.1).
- **No module loading, fail-safe**: `tb.Cable`, `tb.Bridge`, `tb.Impair` and the other builders first check that the
  kernel already has the needed kind (listed in `/lib/modules/<release>/modules.builtin`, or loaded per
  `/proc/modules`: `veth`, `bridge`, `nf_tables`, `sch_netem`, …) and otherwise end the test as "not run: module <name>
  not loaded", never creating the link (which would auto-load the module, 8.1). Only the PC gate's run N sets
  `NMB_TESTBED_ALLOW_MODULE_LOAD=1` to skip that check, so a box run without the right variables still loads nothing.
  P-02's runner sets `NMB_TESTBED_ON_BOX=1`, which selects the box scope below.
- **Scope and cost**: in box mode only tests marked `tier.Feature("box")` run (the 6B.5 list: firewall, DNS, DHCP,
  routing; their owners N-02, N-12, N-04/N-05, N-01 mark them), one at a time (`-p 1`), with reserved addresses only;
  each namespace is removed when its test ends.
- **Detected at run time**: when the box's kernel or P-02's sandbox (systemd `RestrictNamespaces=`, seccomp) refuses
  `CLONE_NEWUSER`, every netns test is "not run: user namespaces refused" with the errno, and the not-run report
  (5.7.3) goes into P-02's verdict; whether a not-run blocks the update is P-02's rule, not F-06's. Allowing user and
  network namespaces in the test run's sandbox is P-02's (and P-07's for the self-test) configuration.
- **Proof**: F-06 proves box mode on the PC with a fake module list and in the `debian-amd64` guest
  (`TestNetnsBoxModeInGuest`: the netns tier's own tests run as an unprivileged guest user with
  `NMB_TESTBED_ON_BOX=1`, `/proc/modules` compared before and after). The run on the real box is P-02's and P-07's
  (and P-13's on the Pi 4); F-06 never touches the box.

5.5.2 Recorded exchanges: a fake can run from an exchange file (F-07's vector format in `spec/vectors/`; F-06 does
not define the format, it reads what F-07 fixes): an ordered list of expected requests and the replies, with
placeholders for values that vary (ports, cookies, times). A request that does not match fails the test and prints
the first difference. Captures of real traffic made by the owning packages are rewritten to reserved values before
they are committed (QB 8; the box's real database copies in `~/nmb-logs` are never used).

5.5.3 Protocol knowledge belongs to the owning package's brief (two sources each, work plan 2.2 point 5); F-06
provides the framework, the RFC-defined fakes (`dhcp4`, `pppoe`, `icmp`, `dns`, `stun`, `http`, `smtp`) and the engine
fakes as their owners specify them (section 12, split).

5.5.4 In-memory frame transport (unit tier for the L2 fakes): `l2.Segment` is an Ethernet segment in memory; each
port has a MAC from `reserved` and exchanges whole frames (`[]byte`, at most 1,518 bytes plus an optional VLAN tag;
longer frames are refused like a real NIC's MTU) with destination filtering (own MAC, broadcast, multicast the port
joined). Both the fakes and `fakenet.PacketSocket(link, ethertype)` (F-04d 4.1.7) are ports of a segment, so N-04's
or N-05's code that takes F-04's packet socket meets `fakes/dhcp4` or `fakes/pppoe` without a kernel. Delivery is in
order per sender, delays and loss come from the fake clock and the script, and every frame is recorded for
assertions. The fakes' frame code is the same in both tiers: only the port differs (a `FrameConn` with `ReadFrame`,
`WriteFrame`, `HardwareAddr`, internal to the test bed).

5.5.5 ICMP echo fake (F-00's brief lines 313-314 left "tests needing ICMP get fakes from F-06"): unit tier: an
in-memory responder behind `fakenet.RawICMP(family, link)` and behind the datagram-socket form, answering echo
requests by the script: loss (a rate or an exact pattern), delay (on the fake clock), duplicate, reorder, wrong
identifier or sequence, truncated reply, TTL exceeded from a named hop, destination unreachable. Netns tier: the
kernel of the answering node replies (with `tb.Impair` netem for loss, delay, duplication, reordering), or, for the
behaviours the kernel cannot show (wrong identifier, truncation, a forged hop), the scripted responder on a raw socket
in that node with the node's own echo replies off (`net.ipv4.icmp_echo_ignore_all=1`, `net.ipv6.icmp.echo_ignore_all=1`
in that node only). The echo parser of the fake is fuzzed (`FuzzICMPEcho`).

### 5.6 QEMU guest runner

5.6.1 One run = one guest, one lock, one throwaway disk. The runner takes the lock first and keeps it to the end:
`flock(2)` `LOCK_EX` on the file named by `NMB_QEMU_LOCK`, waiting at most `NMB_QEMU_LOCK_WAIT` (default 30 min);
when the wait runs out the run is "not run: lock held" (never a second guest). While this brief was written, other
packages' guests held the lock for more than ten minutes at a time (8.1), so the wait is normal, not an error.

**No default path.** The lock is shared with every other agent's guests on the PC, so it must be the one file they
all use; a default would be wrong in exactly the case that matters: F-00's `nmb_hermetic` sets `HOME` to a fresh
empty folder for every run, so a default under `$HOME` would lock a private new file and give no mutual exclusion
(REQ-WP-0029), and it would also be a developer path in the code (QB 8). So: when `NMB_QEMU_LOCK` is unset the guest
tier is "not run: NMB_QEMU_LOCK unset" (5.7.3); a set value must be an absolute path of plain characters, outside the
repository, and, inside a test binary (`testing.Testing()`), not under the run's `HOME`, `TMPDIR` or `GOTMPDIR`
("not run: NMB_QEMU_LOCK under the hermetic HOME"). `tools/guestrun`, run by a person from a shell, accepts any
absolute path outside the repository. `tools/test.sh` reads the value from its caller's environment before
`nmb_hermetic` and passes it in (5.10 point 1); `docs/DEVELOPMENT.md` gives the value this PC's agents use
(`~/nmb-work/qemu.lock`) as the example to put in one's shell profile.

**Lock lifetime = QEMU's lifetime.** A `flock` lock belongs to the open file description, so it lasts while any
process holds a copy of the descriptor (checked: a lock taken by a shell that was then killed with SIGKILL stayed held
by its child until the child ended, 8.1). The runner therefore (1) passes the lock descriptor to QEMU
(`exec.Cmd.ExtraFiles`), so that a guest that outlives a crashed runner still holds the lock and no second guest can
start beside it, and (2) sets `SysProcAttr.Pdeathsig = SIGKILL`, so that QEMU dies with the runner and the lock then
ends with it. Go's `Pdeathsig` fires when the **thread** that started the child exits, so QEMU is started from a
goroutine that holds `runtime.LockOSThread` until QEMU has been waited for. On a normal end the runner waits for QEMU,
then closes its own copy.

gives access. The runner does not call `sg` itself (no host tool); `tools/guestrun` documents `sg kvm -c` and the
gate script may use it (question Q2 for a permanent fix). ARM guests always use TCG on this x86 host.

5.6.4 Networks. Default: two QEMU user-mode networks with `restrict=on` (no outside access), LAN
`198.51.100.0/24` and WAN `192.0.2.0/24`, MACs `02:00:00:<profile>:<run>:<nic>` (from I-01..I-03). For tests that
cable a guest to fake servers or to other nodes: QEMU is started **inside a netns test bed** and its NICs are taps
there (`-netdev tap,ifname=…,script=no,downscript=no`); the taps are ports of the topology of 5.4, so a guest's WAN
port meets the fake ISP node and its LAN port meets namespace clients, all without root (taps work in the user
namespace, and QEMU with KVM started inside `unshare -rn` under `sg kvm`, with a tap made there as its third NIC: the
guest saw `eth2` and the tap counted 250 bytes from it, 8.3). Guest-to-guest cables are not needed while only one
guest runs.

**Deviation from REQ-TS-0008, stated.** The requirement (TESTING 18, the Python VM-D13) names "user-mode NAT as WAN, a
socket link as LAN". The test bed keeps user-mode NAT for the WAN but with `restrict=on`, and replaces the socket link
by a tap into a namespace topology. Reasons: (1) every test run is hermetic and offline (REQ-WP-0047, F-00's offline
runs), and an unrestricted user-mode NAT reaches the internet; when a test needs an "upstream" behind the WAN, the
fake ISP node of `RouterBox` gives it over a tap instead. (2) A QEMU socket link (`-netdev socket` / `dgram`) joins two
QEMU processes; with one guest at a time (REQ-WP-0029) there is no second VM to join, and what VM-D13's LAN carried,
traffic between the box and LAN clients, is carried by the tap: its far end is a bridge in a namespace with the
clients and fakes, and it counts bytes per cable (REQ-TS-0177). Clients inside the guest's own namespaces (VM-D13's
"clients in network namespaces") remain possible in the Debian guest (full iproute2, I-06 §7). The requirement's
substance (a WAN, a separate LAN, simulated radios, namespace clients) is met; its two QEMU mechanisms are not used.

5.6.5 Control and limits:
- **Serial console** on a Unix socket with a **short relative path** (`serial.sock` in the run folder, QEMU started
  with that folder as working directory): an absolute path over 107 bytes is refused by QEMU ("UNIX socket path …
  is too long"), seen on this PC (8.1).
- **Driver in Go** (no Python): waits for byte markers (never character offsets: I-01 run 2's UTF-8 offset bug),
  sends input in 32-byte pieces with 50 ms gaps (I-01 run 3: a 500-character line was cut), wraps each step as
  `<cmd>; echo <MA''RK><n>=$?` with a marker random per run (so console text from the guest cannot fake a result),
  split by quotes in the typed line so that the console's echo of the input never contains the marker itself (the
  trial driver of 8.3 matched its own echoed command and lost the result); after the marker it looks for the prompt
  in the bytes already read before reading more; reads with a bounded buffer (1 MiB per step; more is an error).
- **Debian console**: the Debian image has no shell on `ttyS0` by itself (the kernel line masks
  `serial-getty@ttyS0.service`, I-06 §12 run 1: the getty took over the console and hung up other output; I-06 never
  had an interactive console, its `nmb-probe.service` printed and powered off). `tools/testbed-prepare.sh` therefore
  adds a test-only unit `nmb-console.service` to the disk: `ExecStart=/bin/sh -l`, `User=root`,
  `StandardInput=tty-force`, `StandardOutput=tty`, `StandardError=tty`, `TTYPath=/dev/ttyS0`, `TTYReset=yes`,
  `TTYVHangup=yes`, `Restart=always`, `Environment=TERM=dumb`, `Conflicts=serial-getty@ttyS0.service`,
  `After=sysinit.target`, `WantedBy=multi-user.target`; the getty mask stays on the kernel line so agetty never fights
  it. There is no login and no password: root's password stays locked as mmdebstrap leaves it, no SSH server is
  installed, and the only way in is the console socket in the run folder (mode 0700). The unit exists only on the
  test-bed disk, never in a product image. OpenWrt needs none: procd's console asks for Enter and gives a root shell
  without a password (I-01..I-03 §12).
- **Readiness** (each profile has its probe and its own limit, separate from the per-step limit; the probe polls every
  5 s): OpenWrt: `procd: - init complete -` in `logread` **and** `ubus call network.interface dump` showing the
  profile's interfaces (`lan`, `wan`) `"up": true` (`ubus call system board` answers as soon as ubusd runs, long
  before: I-03 §12 run 1 has `init complete` at about 420 s and `br-lan` at about 361 s, run 2 by 573 s, run 4 by
  622 s; I-02 by 288 s; I-01 109-162 s). Debian: `systemctl is-system-running --wait` printing `running` (or
  `degraded`, recorded with `systemctl --failed` as a finding). Limits: OpenWrt x86-64 KVM 120 s, x86-64 TCG 300 s,
  ARM TCG 900 s; Debian KVM 120 s, TCG 300 s (I-06 §12: startup 2 min 11 s under TCG). Tests start only after
  readiness.
- **Time limits** (all knobs, validated): lock wait 30 min; console ready: x86-64 KVM 120 s, x86-64 TCG 240 s, ARM
  TCG 600 s (I-02: 76 s to the console; I-03: 48-68 s); readiness as above; each step its own limit (default 120 s)
  and one printed line (REQ-TS-0208); whole run 45 min.
- **Clean shutdown**: `poweroff`, then wait for `reboot: Power down` and QEMU exit 0 within 120 s; else SIGTERM,
  then SIGKILL after 10 s, and the run is reported `unclean` (its test results still count, the shutdown is a
  finding).
- **Memory**: the profile's memory must be ≤ 512 MB (the runner refuses more) and `MemAvailable` must exceed it by
  200 MB at start, else "not run: memory" (at the time of 8.1 about 680-1,000 MB were available).

### 5.7 How a test declares where it runs, and the not-run report

5.7.1 Tiers: `unit` (default: PC user mode and QEMU user mode, F-00's runs A-G), `netns` (amd64 on the PC, new
run N; it covers user, network, mount and time namespaces), `guest:<profile>` (run Q), plus features `hwsim`, `kvm`,
`kernel-ppp`, `procd`, `systemd`, `landlock`, `users` (several uids, 5.4.1), `box` (runs in box mode, 5.4.7).

```go
func TestFirewallLanReachesSSH(t *testing.T) {
	tier.Need(t, tier.Netns)                     // skipped with a recorded reason outside the netns run
	...
}
func TestAccessPointWPA3(t *testing.T) {
	tier.Need(t, tier.Guest("debian-amd64"), tier.Feature("hwsim"))
	...
}
```

5.7.2 `tier.Need` reads `NMB_TESTBED_TIERS` (set by the gate per run; validated list) and, when the tier is not part
of this run, calls `t.Skip` with one machine-readable line: `NMB-NOT-RUN tier=<tier> feature=<f> test=<name>
reason=<why>`. A plain `t.Skip` without `tier.Need` is refused by `hermeticcheck` (no silent skips).

5.7.3 Reporting: the gate runs `go test -json` and `tools/testbed-report` (part of `tools/guestrun`) collects
`NMB-NOT-RUN` lines into `testbed.tsv` and the summary: "not run" tests are listed by tier and reason, never counted
as passed. A test that is declared for a tier and did not run in that tier in the package's gate leaves its
requirement ids without proof (work plan 2.4); the gate shows them. Results of the netns and guest tiers carry
`simulated` and the profile (image hash, accel, kernel) (REQ-TS-0011, REQ-CT-0002).

5.7.4 Where each tier runs: unit everywhere (also on the box in P-02's sandboxed test run); netns on the PC (amd64,
and the optional ARM run inside host-made namespaces, 5.4.4), inside guests, and on the box in P-02's sandboxed run
in box mode (5.4.7, roadmap 6B.5); guest on the PC (or a rented server, REQ-WP-0037), never on the measuring box.

### 5.8 `tools/hermeticcheck`

A `go/analysis` checker. REQ-CL-0234 is about the unit tests themselves ("no system tools, no real commands, no
internet, … no time-of-boot or wall-clock boundary"), so it checks test files as strictly as product files.

**Real-clock calls** (the list both kinds of file share): `time.Now`, `time.Sleep`, `time.After`, `time.AfterFunc`,
`time.Tick`, `time.NewTimer`, `time.NewTicker`, `time.Since`, `time.Until`, `context.WithTimeout`,
`context.WithDeadline`, `context.WithTimeoutCause`, `context.WithDeadlineCause`.

| Rule | Product files (non-test) | Test files (`_test.go`) outside `internal/testbed` |
| :--- | :--- | :--- |
| real-clock calls | refused outside C-05's clock implementation | refused (tests use `FakeClock`) |
| `os/exec`, `os.StartProcess`, `syscall.Exec`/`ForkExec` | refused outside F-04's runner implementation | refused (commands come from `fakeexec`; child processes from `host.ReExec`) |
| absolute paths in string literals under `/proc`, `/sys`, `/run`, `/etc`, `/var`, `/dev` (except `/dev/null`), `/tmp` | — (product paths come from `Layout()`) | refused (machine files come from `fakesys`; folders from `host.Layout`/`t.TempDir`) |
| `net.Dial*`, `net.Listen*`, `http.Get`/`Post` and `(*net.Dialer)` calls with a literal address that is not loopback or from `reserved` | — | refused |
| `os.Getenv`, `os.LookupEnv`, `syscall.Getenv` | refused outside the configuration loader | refused (tests set values with `t.Setenv`) |
| imports of `internal/testbed` | refused | allowed |
| `t.Skip`/`t.SkipNow`/`t.Skipf` without `tier.Need` | — | refused (no silent skips) |
| literal IP addresses, MACs and host names not from `testbed/reserved` | — | refused (complements F-00's privscan) |
| a test package under `internal/` or `cmd/` without a `TestMain` that calls `host.Main` | — | refused (5.2.2) |

**Allowed places** are a short list in the checker, each with its reason, and the list is printed by the checker's
`-allowed` flag so the verifier can read it: `internal/testbed/clock` (`BlockUntilWaiters` waits in real time, bounded,
5.1.2); `internal/testbed/tier` (the real-time "test hung" guard below); `internal/testbed/netns` and `host` (`os/exec`
for the re-exec, `newuidmap`/`newgidmap`); `internal/testbed/guest` (`os/exec` for QEMU, real timeouts of 5.6.5,
`/dev/kvm`, `/proc/meminfo`); `internal/testbed/fakesys` (reads its own fixture trees); C-05's clock; F-04's runner;
F-00's `tools/` (written before the test bed; `os/exec` and real time in its own checkers).

**Real network deadlines and the fake clock.** The fake clock never drives kernel sockets. In the netns and guest tiers
a test may wait for real network traffic only through `tier.RealDeadline(t, d)`, a context on the real clock that
exists to fail a hung test ("test hung after d"), never to decide a result; `d` is a knob scaled for TCG. Product
code under test bounds its own I/O by its `Clock`'s `WithTimeout` (4.2): with the fake clock in the unit tier the test
advances time and the product cuts the I/O; in the netns tier, where real packets flow, the product gets C-05's real
clock (the namespace tier tests behaviour on the wire, not timing logic, which the unit tier covers).

Analysis test data (`testdata/src/…`) holds a positive and a negative case for each rule and each file kind, test
files included (`TestFlagsTimeNowInTest`, `TestFlagsExecInTest`, `TestFlagsProcPathInTest`, `TestFlagsDialNonLoopback`,
`TestFlagsContextWithTimeout`, `TestAllowsReservedDial`, `TestFlagsMissingTestMain`, …). Wiring into
`tools/analyse.sh` is an integrator change (5.10).

### 5.9 Byte order, 32-bit, resources

- Byte order: netlink native (explicit `binary.NativeEndian`), every protocol fake big-endian on the wire
  (`binary.BigEndian`), tar and results parsing by the standard library. 32-bit: the clock's `Mono` is `int64`
  updated under a mutex (no unaligned 64-bit atomics on arm v7 and mips); netlink structs packed by hand, no
  `unsafe` casts.
- Resources on the PC: a namespace costs a few MB (on the box in box mode the same, one test at a time, 5.4.7); the netns run uses `-p` = `NMB_GATE_JOBS` (default 2); fakes
  hold at most a few MB of buffers. A guest: 256-512 MB and QEMU's own memory (another package's 512 MB KVM guest had
  401 MB resident two minutes after start, `ps` during 8.1; resident memory grows as the guest touches its RAM, so
  the 200 MB margin of 5.6.5 is on top of the full guest size). Pi 4 budget: the test bed is not shipped in `nmbd`
  (test-only code); its unit-tier helpers must still finish in the arm64 user-mode run within ten times the amd64
  run's time (a limit to measure in F-06's own gate, not yet measured).
