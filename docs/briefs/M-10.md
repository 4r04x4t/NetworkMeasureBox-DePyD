# Brief M-10: Ookla engine

Analyst's brief for package **M-10** of `docs/NATIVE_WORK_PLAN.md@ad3758c:145` (measuring packages, section 3.2;
"Ookla engine (see section 7)", roadmap 4.3). No code is written by the analyst. This is an **early brief**: its
weight is on Ookla's terms and licence (read first, work plan section 7 point 3, REQ-WP-0181), the program's behaviour
(messages, phases, timings, output, exit codes, refusals, licence and GDPR prompts), the server choice, the data use
per run, the sandbox the program needs, the refusal pause rules from fixes and the faults of the Python engine. The
runner (M-04: schedule, cancel, traffic gate, caps), the pause and caps (M-05) and the F-04 contracts are drafts; what
this engine needs from them is written as "expected from M-04 / M-05 / F-04" (section 8) and every difference is listed
under *Blocked* (section 13). The runner and the pause are not designed here.

Written 2026-11-11 on the development PC (Windows, WSL2 Ubuntu 24.04). Python reference: the Python repository at
`ad3758c` (read only), cited `<file>@ad3758c:<line>`; it is the intended behaviour, never its faults (Quality Bar 6).
Every place where it is wrong is marked **"Python does X; correct is Y"**. The owner's decisions (Python repository
`bb0a553`, `docs/NATIVE_WORK_PLAN.md` section 7, points 1-24) were read and applied. F-04, F-05 and F-06 are drafts in
`~/nmb-work/wt/F-0x/docs/briefs/` (F-04 at `ac460d4`, read 2026-11-11 16:00-17:30 UTC); they are cited by part and
section, not by line, because the lines still move.

**Revision 3 (2026-11-11):** the owner's and the orchestrator's decisions of 2026-11-11 are written in (table below;
no owner question is left, section 14), and the eleven findings of the second review are fixed (install folder on

Consequences this brief draws from them (analyst; no owner question left):
- A migrated Python acceptance has neither the personal-use confirmation (D-02) nor a program version (D-06), so a
  migrated box asks again before Ookla runs (old Q-10; 4.1, T-M10-03).
- No worldwide server search: it needs Ookla's website API, which the Terms forbid (6.1 item 6) and which Python
  reached only with a browser `Referer` (D-11) (old Q-04; 4.4).
- The real program is never run on the development PC or in CI: it is downloaded only on the box after acceptance
  (D-05), and live tests run on the Pi 4 (owner's point 5) (old Q-09; 10.5).
- The server list is refreshed on the owner's click and at most once a day while it is shown (old Q-03b; 4.4): a
  design of this brief, recorded under *Changed* in the changelog, because each refresh is an Ookla request (README
  123) and D-12 limits only tests.
- Nothing runs in Ookla's place in an Ookla-only cycle while Ookla may not run (old Q-05): expected from M-04 (B-13),
  on CHANGELOG 307 and REQ-CL-0355 ("no other engine in its place").
- D-12 and the metered rule: "never held back" is read as "not held back by the interval or the hourly limit"; the
  owner's point 14 (a metered link waits for a cap or "unlimited") is a data-cap rule, which D-12 names as a limit,
  so it stays (M-05 decides per link, B-02).

## 3. Source analysis

### 3.1 What the Python engine really does

- **Run** (`ookla.py@ad3758c:394-486`): finds or installs `speedtest`, runs it with `--accept-license --accept-gdpr
  --format=json`, `--interface` (or `--ip`), `--server-id` when chosen, deadline 120 s, environment with
  `HOME=/var/lib/nmb/ookla`. A non-zero exit gives an `error` row with stderr; exit 0 is parsed; **any exception gives
  `None`**, which the caller reads as "the program is missing" (`:484-486`, `:547-557`).
- **Fallback** (`:540-558`): without a result and without a chosen server, `speedtest-cli` (a third-party Python client
  of Ookla's network) runs, and its result keeps the default engine name `ookla` (`:46`, `:516-534`).
- **Install** (`:288-371`): any `speedtest` in `PATH` first, then three fixed paths, else downloads the pinned 1.2.0
  archive for the machine (hashes `:280-285`), checks SHA-256, writes the member `speedtest` into `/opt/nmb/bin` or
  `/usr/local/bin` if writable. `setup.sh@ad3758c:65-77, 197-206` installs it at setup time, before any acceptance.
- **Server list** (`:101-276`): the program's `--servers` (`-L`) without the licence flags and without the home, and
  Ookla's **website API** `www.speedtest.net/api/js/servers` with a browser `Referer` (`:129-148`) and the default
  random browser agent (C-05 NF-1); refreshed in the background when older than 300 s (`:110, 216-223`); a search
  queries the website for every request (`:228-241`); an unknown id becomes a made-up entry with the Hungarian word
  "Egyedi" as country (`:264-274`).
- **Pause and hourly limit** (M-05's `anti_ban.py`, used by `runner.py@ad3758c:273-325`): terms gate, then the hourly
  limit for scheduled runs, then the refusal pause; a refusal is recognised by text (`anti_ban.py@ad3758c:126, 163-166`)
  and doubles the pause 30 min → 4 h; a success resets it.
- **Runner substitution** (`runner.py@ad3758c:1200-1205`): an Ookla-only schedule while Ookla may not run runs
  Cloudflare, Fast.com and RTR instead, each under its own name (tests `test_ookla_honesty.py@ad3758c:280-283, 315-317`).

## 4. Behaviour as intended (with the Python faults marked)

### 4.1 Terms and acceptance (REQ-CL-0102, REQ-RM-1147, REQ-WP-0179, KF-0028)

- **Nothing of Ookla's before acceptance.** Until the owner has accepted, the box does not download, install or run the
  program (not for a test, not for the server list, not for `--version`), and does not contact any Ookla address.
  Reason: "BY INSTALLING THE SOFTWARE, YOU ... ACCEPT THIS AGREEMENT" (S-01); installing it for the owner would accept
  for him. **Python does** download and install the program in `setup.sh@ad3758c:65-77, 197-206` and at run time
  (`ookla.py@ad3758c:288-371`) before any acceptance, and asks the program and the website for the server list without
  acceptance (`:181-204`); **correct is** this rule (NF-M10-1, NF-M10-2).
- **The acceptance screen** (U-02's page, M-10's content): NMB's own plain-language summary in all 11 languages, from
  one source (F-04f keys `speed.ookla.terms.*`), of what Ookla's documents say (section 6.1: personal, non-commercial use
  on a single personal computer; not on a router or modem; no sharing over a network to other devices; Ookla keeps every
  result and may share the IP address, device identifiers and location with internet providers and others), and the
  three links (EULA, Terms of Use, Privacy Policy; F-04e `links`). Ookla's documents are not translated or copied
  (they are Ookla's texts; S-02 "Your Use of Content"). The screen states the EULA's limits (D-02): personal,
  non-commercial use; one personal computer; not on a router or modem; not offered to other devices over the network;
  Ookla results stay off the password-free LAN page and out of collectors run by others (D-03). Three confirmations,
  all required: (1) **personal, non-commercial use** of this box by its owner (D-02; a box set up for a business or an
  organisation does not offer Ookla, S-02 "Businesses ... are not permitted"); (2) the licence and terms
  (→ `--accept-license`); (3) the privacy notice (→ `--accept-gdpr`) †, because the program asks (2) and (3) separately
  (S-07).
- **The record** (expected from F-04a, B-05): accepted (bool), accepted at (UTC), the three confirmations, **the
  program version and archive hash it was accepted for**, the NMB summary text version. A new program version needs a
  new acceptance before it runs (D-06), because Ookla's notices may change with it and the flags would otherwise
  accept the new text for the owner.
- **Who:** the owner role through the API only (F-04a writers `api`); not the bot, the boot copy, USB import or the
  collector. A Python `nmb.conf` with `ookla_terms_accepted = true` was set by the owner (Python starts every install
  as not accepted since `7e10bf4`), but it lacks the personal-use confirmation (D-02), the privacy confirmation and the
  program version (D-06) the native record needs. **So a migrated box asks once again** before Ookla runs (all three
  confirmations, record bound to the program version and hash); past results stay (consequence of D-02 and D-06, old
  Q-10). F-04a decides how the key is migrated (B-05).
- **Withdrawal:** stops every Ookla use at once (a running test is cancelled and stored as aborted), and deletes the
  program and its home (D-07; S-01 *Term and Termination*: "terminate this Agreement by deleting the Software"); past
  results stay (D-07).
- **Where Ookla is offered (D-01):** only on the generic PC/Pi build. The router targets of step 2 do not build the
  engine at all (build constraint; G-M10-4). On the generic build in router mode (mode from C-11's setup record) M-10
  starts nothing, offers nothing and answers `unavailable{router_mode}`; on the switch into router mode the program
  file is removed † (EULA (f) forbids installing it on a router), the acceptance record and the home stay, and the
  program is downloaded again (same pin, same version check) after the box leaves router mode.
- **Engine state for the UI** (`ookla.State()`): `terms_required`, `not_installed`, `installing`, `ready`,
  `paused{until}` (from M-05), `unavailable{reason}` (no archive for this machine, hash mismatch, home unwritable,
  `router_mode`).

### 4.2 Getting the program (REQ-RE-0294, REQ-CL-0406, REQ-RM-1208, KF-0080, KF-0079)

- Only after acceptance, started by the owner's action (the accept button starts an `ookla_install` job †).
- Through P-02's verified download path (expected from P-02, B-03): URL `https://install.speedtest.net/app/cli/
  ookla-speedtest-<version>-linux-<arch>.tgz`, arch from `runtime.GOARCH` (amd64 → `x86_64`, arm64 → `aarch64`; others
  `unavailable` in step 1), **pinned SHA-256** per arch in `spec/engines/ookla.json` † (1.2.0: x86_64 `5690596c...eeb7`,
  aarch64 `3953d231...31bd3`; S-06 and `ookla.py@ad3758c:280-285`), size limit 8 MiB † (archive 1.1 MB), the request
  with the own user agent `NetworkMeasureBox/<version>` and no browser headers (D-11). **This brief expects the
  download outside C-05's custom scope**: it goes through P-02's verified download path, which always sends the own
  identity, because it is not a measurement and it reaches Ookla's install server, not a test server. C-05's draft
  (3.4 scope list and call-site table, Q8) puts "the download of the Ookla program" and the server list into M-10's
  custom scope; the server list no longer makes an HTTP request of NMB's own (4.4), so M-10 has **no** request in the
  custom scope. The difference is B-14.
- **A refusal of the download** (D-09): when P-02 reports HTTP 429 or 403 from Ookla's install server, M-10 reports
  `RecordRefusal(retry_after)` to M-05 (the same Ookla pause, at least the `Retry-After` the answer gave), the install
  job ends as failed with reason `ookla_refused` and nothing is retried until the pause ends. The install job is an
  Ookla request under the same gate (`Allowed(trigger, install)`, `RecordAttempt(install)`, 8.2). The status code is

- The archive is parsed by a limited tar/gzip reader (fuzzed): only the regular member named exactly `speedtest`, at

  for the licences page (P-08). Not under `/usr`: the root file system of NMB's own image is read-only and updated as an

- **Before every start** the binary's SHA-256 is checked against the pin recorded at install † (2.6 MB: a few ms on the

- **Python does** take any `speedtest` from `PATH` or three fixed folders without a check (`ookla.py@ad3758c:295-308`;
  `setup.sh@ad3758c:66`), so another program of that name (the `speedtest-cli` package installs one) or a changed file
  would run; **correct is** only the pinned file (NF-M10-5). **Python does** read the whole download into memory without
  a size limit (`ookla.py@ad3758c:354-355`; private audit 2026-11-10, engines item 6 category); **correct is** the limit.
- NMB never ships the program in an image or package (EULA (e), section 6.1); P-11 and I-0x images contain no Ookla file

### 4.4 Server choice (REQ-RM-1112, REQ-RE-0072, REQ-CL-0108, REQ-TS-0144, REQ-CL-0376, QB 9)

- **Automatic** (default `server_id = auto`): the program picks the nearest server by latency from where the box is
  (S-06, S-05 "local server"): location-aware by design, no list and no country in NMB (G-M10-2: no Ookla server id or
  country table in code, data or tests other than reserved test values).
- **Chosen:** the owner picks from the list or types an id; it is passed as `--server-id`. The id is never swapped:
  **no rotation and no quarantine** (KF-0093; the Python code for them is dead, `anti_ban.py@ad3758c:22-121, 199-249`).
  A result whose `server.id` differs from the chosen id is stored with `requested_server_id` in the raw record and
  shown (REQ-CL-0376; `runner.py@ad3758c:867-877`). A chosen id that Ookla does not know gives the failed row with
  reason `server_not_found` (recorded answer: `Configuration - No servers defined (NoServersException)`, exit 2, S-07)
  and a clear text (REQ-TS-0144); it does not fall back to automatic.
- **The list** comes only from the program: `speedtest --servers --format=json` (S-06 `-L`), under the same gate as a
  test (terms, installed, M-05 `Allowed(list)`), in the same sandbox and home. Its JSON form is not in S-06 and has no
  recording yet (B-10): the parser accepts `{"servers":[{id, host, port, name, location, country}, ...]}` † with limits
  (≤ 100 entries, strings ≤ 128 bytes, id 1..2^31-1, port 1..65535) and refuses anything else.
  - Cached on disk `<STATE>/speed/ookla_servers.json` with `fetched_ts` (F-04e `speed.servers` answers from the cache).
  - Refreshed **on the owner's click** (REQ-CL-0088, job `servers_refresh`) and automatically only when the cache is
    older than 24 h † and the list is being shown (against REQ-RE-0072's "every few minutes": a consequence of the
    decisions, recorded under *Changed*; see the decisions table); never during a pause (the click answers 409
    `paused` with the time left), never before acceptance (`terms_required`).
  - Each list fetch is reported to M-05 as an Ookla request (`RecordAttempt(list)`; README 123: "the server list refresh
    also asks Ookla"); whether it counts toward the hourly limit of scheduled tests is M-05's (B-02).

### 4.6 What the row says, binding and the link

- `server_id`, `server_name`, `server_host` (`host:port`), `server_location` (`location, country`), `server_ip`
  (`server.ip`, REQ-CL-0007): strings limited (F-04b ≤ 256), control characters refused. An absent or empty field is
  stored as **NULL**: no name → `server_name` NULL; no host → `server_host` NULL (a port without a host gives no
  `host:port`); `server_location` only from the parts present (`location, country`, `location` or `country`), NULL
  when both are absent. **Python does** store the English word "Unknown" for a missing name in every language, the
  empty string for a missing location and country, and `None:<port>` for a missing host
  (`ookla.py@ad3758c:446-448`); **correct is** NULL (NF-M10-19; REQ-CT-0004 "no value not measured").
- `client_ip` / `client_ipv6`: `interface.externalIp`, only a global address (C-05 `SplitGlobal`; M10-L4).
- **Binding (REQ-RM-0027, REQ-TS-0156, KF-0231):** the program only "attempts" to bind (S-06). After the run,
  `interface.name` must equal the asked interface (when `--interface` was given) and `interface.internalIp` must be an
  address of that interface at start (M-04's link record); otherwise the row is failed with reason `bind_mismatch` †
  and keeps **no measured values** (a result of another link is no measurement of the asked one). The data the run
  used is not a measured value and is kept: `bytes_down`/`bytes_up` stay in the row and are counted by M-05 against
  the interface the program actually used (`interface.name`, when it is an interface of the box in M-04's link
  record), because those bytes went over that link, which may be metered (owner's point 14, KF-0294); when
  `interface.name` names no interface of the box, they are counted against the asked link and an event is written,
  so no byte is lost from a cap † (M-05's interface counters, section 5, count the real traffic as well). **Python
  does** store the asked interface whatever the program used (`ookla.py@ad3758c:457`); **correct is** the check
  (NF-M10-17).
- **VPN:** `interface.isVpn = true` (6 of 130 recorded rows, S-07) is kept in the raw record and passed to C-11's setup
  as "measured through a VPN" † (B-08); **Python does** drop it; **correct is** to keep it (NF-M10-18).
- **Result link (REQ-RM-1157):** `result.url` only when `result.persisted == true` and the URL is
  `https://www.speedtest.net/result/...` (≤ 2048 bytes); otherwise NULL. **Python does** store `result.url` without
  looking at `result.persisted` (`ookla.py@ad3758c:475`), so a link to a result Ookla says it did not keep can be
  shown; **correct is** this rule (NF-M10-21).
- **Who sees Ookla rows (D-03):** the owner's views, exports and the owner's own dossier only. The password-free LAN
  results page (F-04e 4.3.4, public results) leaves Ookla rows out, and the collector client (S-12) sends no Ookla
  row to a collector run by someone else. M-10 marks the rows by `engine = ookla`; the filters are F-04e's and S-12's
  (B-16).
- **Raw record:** an allow-list copy of the result (`type, timestamp, ping, download, upload, packetLoss, isp,
  interface.{name,isVpn,externalIp}, server, result`) plus `requested_server_id` and `measurement_cpu`; **not**
  `interface.macAddr` and `interface.internalIp` (the local address is in `bound_ip`). **Python does** store the
  program's whole output, with the box's MAC address and LAN address, in every row (`ookla.py@ad3758c:476`;

  privacy: a row keeps what the measurement needs). Owner's point 22 is not the basis: it keeps MAC addresses in the
  SLA dossier and the ISP-support bundle and pseudonymises them only in bundles for outside LLMs; it says nothing
  about stored rows. If the setup or the dossier needs the measuring interface's MAC address, it comes from the box's
  own link record (C-11's setup record, read from the kernel), not from Ookla's output; C-11 does not list it today

- **User agent:** the program sends Ookla's own identity, which NMB does not change and which the custom value never

## 5. Data use per run (for the data caps, M-05)

- **What moves:** configuration and server selection (latency probes to a few nearest servers), the two transfers, and
  the result upload (compressed, S-06). The program sizes the transfers itself.
- **Recorded (S-07, one gigabit-class line, 130 runs):** per direction `elapsed` 3.7-15.0 s (median about 7 s; the
  largest 15,012 ms download and 15,008 ms upload), and `bytes / bandwidth` up to 15.17 s (download) and 14.67 s
  (upload); rates 105-944 Mbit/s down and 18-327 Mbit/s up; download 0.15-1.5 GB (median 0.74 GB), upload
  0.01-0.43 GB (median 0.28 GB); a whole run 0.17-1.83 GB, **median about 1.0 GB**. Ookla's own example (S-06, near
  1 Gbit/s both ways) shows 117.5 MB and 114.8 MB, so the size varies widely with the line and the server. The time
  per direction is **observed on one line, not documented**: S-06 gives no test duration (only the 10 s request and
  15 s latency timeouts), and a new program version may change it.
- **Requirement on the figure M-05 checks before a run** (`Check`; M-05 decides how, B-02): it must **never be below
  what the run can move**. A measured rate is not a maximum: after a slow run (congestion, a degraded line, a partial
  run, a slow server) on a line that is now fast, the last result undercounts by orders of magnitude (10/2 Mbit/s
  would give about 32 MB against the 1.83 GB recorded), and `Check` would admit a run that overruns the remaining cap
  of a metered link (owner's point 14, KF-0294). A figure is therefore a **bound** only when every input is a
  maximum:
  - per direction `R_max = max(the link's nominal or negotiated rate, the highest Ookla rate ever recorded on that
    link)`, never the last result alone;
  - `bound = (R_down_max + R_up_max) / 8 × T + 10 MB` †, with `T = 20 s` † per direction (about 30 % above the
    recorded 15.17 s of `bytes / bandwidth`; observed, not documented);
  - at 1/1 Gbit/s that is about 5.01 GB; at 100/20 Mbit/s about 0.31 GB;
  - a run whose `bytes` exceed its bound, or a direction longer than `T`, is an event and raises the bound for the
    next check †; `T` is measured again for every new program version (L-3);
  - without any maximum (no nominal or negotiated rate known) the figure is only an **estimate**, and M-05 must not
    use it as a bound (B-02).
- **After a run:** the program's `download.bytes + upload.bytes` go to `bytes_down`/`bytes_up` and to M-05's count
  for the link the program used (also after `bind_mismatch`, 4.6, and after `partial`); M-05 also counts the interface
  (the program's control traffic is not in `bytes`).
- **A refused run:** answered after about 0.09 s (S-07), a few kilobytes †. A server-list fetch: small, to measure on the
  Pi 4 (L-3).
- **Metered link** (owner's point 14, KF-0294): no Ookla run, scheduled or by a person, until the owner set a cap or
  "unlimited" (M-05). This is a data-cap rule, which D-12 keeps as a limit; D-12's "a person's test is never held
  back" is read as "not by the interval or the hourly limit" (decisions table; M-05 decides per link, B-02).

## 9. Design

### 9.1 Packages and the split

`internal/engines/ookla` †: `terms.go` (acceptance record, version binding), `install.go` (asks P-02, tar member
extraction, hash before start), `argv.go` (fixed argument list), `run.go` (one run through F-04d's runner),
`classify.go`, `parse.go`, `servers.go` (list, cache), `home.go` (home check and migration). About 900-1,300 lines with
tests †. The Python reference is 558 lines and one program: **no split needed**; if the contracts arrive late, the
order is (a) parse/classify with goldens, (b) terms and install, (c) run and list.

### 9.2 Concurrency

One program process at a time (M-04's lock; a list refresh takes it too †, so it never runs during another engine's
test); `Run` blocks until exit, deadline or cancel; parsing is single-threaded; the cache file is written atomically by
one writer (F-04c rule).

### 9.3 Detected at run time

Architecture (`runtime.GOARCH`), the installed version and its hash (install record), whether the home is writable,
the kernel's `SO_BINDTODEVICE` behaviour (a probe socket at start-up †), the CA bundle path (first of S-06's list that
exists, passed with `--ca-certificate` only when none of the default paths exists †).

### 9.4 Byte order and 32-bit

JSON numbers decoded as `json.Number` and converted with range checks: bandwidth and bytes as int64 (bytes above 2^31
were recorded), ms as float64 then rounded to int64 µs; no `int` for sizes; all on `linux/arm` and `mips` cross-builds.
No binary formats except tar/gzip (standard library, limited).

### 9.5 Resource budget on the Pi 4 (estimates †, to be measured, L-4)

NMB side: under 2 MiB extra heap per run, negligible CPU. The program: binary 2.6 MB on disk; RSS to measure (cgroup
`memory.peak`); CPU is the program's (on the recorded line near 1 Gbit/s the box peaked about 80 % with one core at
100 % and soft-IRQs up to 62 %, S-07 `measurement_cpu`): recorded per row, never optimised by M-10.
