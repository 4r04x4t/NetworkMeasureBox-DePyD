## 4. Review against the fault register (before any case is used)

Each case file carries a `review` block (5.1). The verdicts:

| Verdict | Meaning | `expected` |
| :--- | :--- | :--- |
| `same` | Python's output is the intended behaviour | equal to `python` |
| `python_wrong` | Python records a known fault; KF id (or proposal id) required | the correct output, different from `python` |
| `open` | it is not known yet (owner question, missing F-04 contract) | absent; the case does not gate a native package until closed |
| `not_comparable` | Python cannot produce it (for example it raises where the native build must load) | the correct output; `python` holds the exception |

Rules (checked by T-REV-1..5):

1. The reviewer goes through every KF entry whose *Package that proves it* or *also* list names the case's owner
   package, and through the proposals of section 12 that touch it; the case lists the ids it was checked against
   (`checked_kf`) and the register commit (`register`).
2. `python_wrong` and `not_comparable` name at least one KF id that exists in the register at that commit, or a
   proposal id `F05-Pnn` from this brief until F-03 gives it a KF id.
3. A `python_wrong` case whose `expected` equals `python` is an error (a fault frozen).
4. When the register file changes (new commit), the check fails for every case that names an older register until
   it is reviewed again (the reviewer updates `register` after reading the new entries of its package).
5. The verifier of a component package re-reads the review of its cases; the reviewer is never the implementer of

## 5. Design

### 5.1 Where the files live (decision)

One file per case, so the Python output, the intended output and the review cannot drift apart:

```
tests/golden/README.md                  what a case is, how to capture, review and run
tests/golden/cases/<group>/<case>.json  one case: input reference, python, expected, review, provenance
tests/golden/inputs/<group>/...         made-up inputs: SQL fixture scripts, nmb.conf files, hex packets, tool output text
tests/golden/capture/                   the Python capture driver (runs only on the PC, never in the gate)
tests/golden/goldenfile/                Go package: load and validate cases, compare, write the diff report
tests/golden/check_test.go              the review, schema, privacy and register checks (T-REV, T-CASE)
tests/golden/PHASE0.md                  the Phase 0 table of section 7 with each row's package and test name
tools/pyref.sh                          export the Python reference and run the capture in the sandbox (5.3)
tools/differential.sh                   Python against native on the same inputs (5.5)
```

Case file (canonical JSON: UTF-8, keys sorted, two-space indent, final newline; byte outputs as strings with an
`encoding` field, binary as lowercase hex):

```json
{
  "id": "csv/speed-skipped-and-formula",
  "group": "csv",
  "owner": "R-02",
  "phase0": ["REQ-RM-1215"],
  "input": {"fixture": "inputs/csv/two-rows.sql", "call": "export_speedtests_csv", "args": {"start_ms": 0, "end_ms": 4611686018427387904, "contract_down_mbps": 1000.0}},
  "python": {"output": "timestamp_iso,...\r\n", "encoding": "utf-8", "exception": null, "log": []},
  "expected": {"output": "timestamp_iso,...\r\n", "encoding": "utf-8"},
  "review": {"verdict": "same", "kf": [], "checked_kf": ["KF-0034", "KF-0035", "KF-0129"], "register": "<commit of KNOWN_PYTHON_FAULTS.md>", "note": ""},
  "provenance": {"ref": "ad3758c", "python": "3.12.3", "sqlite": "3.45.1", "driver": "<commit>", "tz_runs": ["UTC", "Pacific/Chatham"]}
}
```

`spec/vectors/` (F-07) is seeded from these: when F-07 is built it moves each reviewed case's language-neutral part
(`input`, `expected`) into its vector format with `git mv`-style history and leaves `python`, `review` and
`provenance` in `tests/golden/` (one copy of each fact; F-07 decides the vector schema, F-05 does not pre-empt it).
Until then the component packages read `tests/golden/cases/` through `goldenfile`.

How a component uses it: its own `*_test.go` (inside its folder, work plan 2.2 point 1) calls
`goldenfile.Cases(t, "<group>")`, runs each case's input through its code and calls `goldenfile.Compare`. So the
cases run in the package's normal test runs A-F of the F-00 gate: amd64, race, two time zones, and arm64 and
arm v7 under QEMU user mode. `goldenfile` itself imports nothing of the product.

### 5.2 Inputs (all made up, reserved values only)

- Databases: SQL scripts that `CREATE` with the Python schema (`nmb/db/schema.sql` plus
  `database.ensure_schema_upgrades`, `nmb/db/database.py@ad3758c:117`) and insert rows. Time stamps are fixed epoch
  milliseconds; addresses from 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32, private ranges only
  where the case is about private ranges; host names under `example.com`/`.net`/`.org`; MACs `02:00:00:...`. Large
  series (a month of ping minutes) come from a seeded generator (Go, in `tests/golden/inputs/gen/`) whose output is
  generated at test time, not committed. The native side opens the same database file through its reader of a
  Python-format database (C-02, REQ-RM-0208), so one fixture serves both sides; where F-04's native schema differs,
  C-02's migration is part of what the case tests, not a second fixture.
- Settings files: the Phase 0 row "every setting with empty, text, negative, huge and `%` values" is generated from
  the keys of `DEFAULT_CONFIG_TEXT` (one file per key and kind), plus hand-written syntax cases.
- Reused Python test fixtures: only after `privscan` with the private list (KF-0059: the Python test data names
  the owner's ISP and places); a fixture with a hit is rewritten with reserved values, never copied.
- Never: the real box's database or logs (memory rule; `~/nmb-logs/` is not read), a capture from the box, real
  tokens. Fake tokens are obviously fake and do not match privscan's token patterns.

### 5.3 Capture on the PC (`tools/pyref.sh`)

1. Refuses root (exit 2, KF-0001); refuses a dirty or missing reference commit. `NMB_SRC` (default
   `$HOME/src/NetworkMeasureBox`) and `NMB_PYREF` (default `ad3758c`); exports with
   `git -C "$NMB_SRC" archive "$NMB_PYREF"` into `build/pyref/<commit>/` (ignored), so the working copy of the
   Python repository is never run and gets no `__pycache__`.
2. Runs the driver as `python3 -I -B` with `env -i` (`PATH=/usr/bin:/bin`, `LANG=C.UTF-8`, `COLUMNS=80`,
   `PYTHONHASHSEED=0`, `PYTHONDONTWRITEBYTECODE=1`) inside a new user, mount and network namespace: loopback only,
   a private tmpfs on `/tmp` (the reference writes caches to a fixed `/tmp` path,
   `nmb/speed/iperf_directory.py@ad3758c:28`), the export bind-mounted read-only, an empty `HOME` in the tmpfs, and a
   nested user namespace mapped back to the real user (as F-00's `nmb_offline`, `tools/lib.sh@5f847a7:223-229`, plus
   `-m`). Seen on the PC: inside, uid is the real one, no capabilities, and `sudo` cannot elevate (section 10).
3. The driver installs `sys.addaudithook` before importing `nmb` and records every `open` outside the export and
   the tmpfs, every `socket.connect`/`socket.getaddrinfo`, every `subprocess.Popen`/`os.system`/`os.exec*`; it
   patches `socket.create_connection` to refuse. Any recorded event fails the case (it is not hermetic, REQ-RM-1058)
   unless the case declares it as the behaviour under test (for example "the lookup is attempted").
4. Each case runs twice, `TZ=UTC` and `TZ=Pacific/Chatham`; different outputs fail the capture (a time-zone fault).
   Wall-clock reads are patched to the case's `now_ms` (`db.now_ms`, `time.time` where a function takes no
   parameter).
5. The script writes only the `python` and `provenance` fields; `expected` and `review` are written by a person or
   agent reviewing (section 4), never by the script. A re-capture that changes `python` of a reviewed case resets
   its verdict to `open` and prints the diff.
6. Then `privscan tree` over `tests/golden/` with `NMB_PRIVATE_VALUES`; without the private list the run is marked
   `private list: not used` and the orchestrator repeats it before merge (F-00 4.5).

Python is a PC tool only: listed in `docs/DEPENDENCIES.md` as `system`, `build only` (python3 3.12.3, PSF-2.0,
with its SQLite 3.45.1, public domain). The gate (`tools/gate.sh`) never needs Python: it reads committed cases.

### 5.4 Privacy of every captured file

| File kind | Risk | Rule |
| :--- | :--- | :--- |
| Inputs | site data typed by hand or copied from Python tests | reserved values only (QB 8); privscan + private list on every capture; reused Python fixtures rewritten |
| `python` outputs | Python defaults and texts that privscan flags or QB 8 forbids (public resolver addresses in the defaults, an address at a real domain, one ISP's router models in help texts) | public service addresses that the defaults name get exact `allow.txt` entries with a reason, reviewed by F-05's verifier; anything else flagged is stored as `{"sha256": ..., "withheld": "<reason>"}`, never as text |
| `expected` | the same | never holds a value that QB 8 forbids (it is the native behaviour) |
| `provenance` | developer paths, user names | only commit ids and version numbers; no paths (privscan `path` rule) |
| differential reports | outputs of fuzz cases or generated inputs | under `build/differential/` (ignored), never committed; the summary that goes into a brief or `docs/TESTING.md` gives counts and case ids only |

### 5.5 Comparison harness (`goldenfile` and `tools/differential.sh`)

Two uses, one comparison code:

- **Gate use (every package):** native output against `expected` of the package's cases. `same`, `python_wrong`
  and `not_comparable` cases gate; `open` cases are run and their result reported, but do not fail. A case of an
  accepted package with no native result fails (no silent skip); a group whose package is not built yet prints
  "not built: N cases".
- **Differential use (PC only, on request and before P-13):** the same input into the Python driver (5.3) and into
  the native adapter, also for inputs that are not cases: generated databases, settings files, and the fuzz corpora
  of the parsers (`testdata/fuzz/<Name>/`, 6B.8 point 4). Each difference is classified:
  - *known*: a case or a rule of the review says Python is wrong there (KF or proposal id given);
  - *finding*: anything else. A finding is written down; it is a fault of one side until shown otherwise, and it
    becomes a case (and a vector for F-07) with a review.

Normalisation, stated per output kind and never wider than this:

| Output kind | Compared as |
| :--- | :--- |
| CSV, `nmb-cli` JSON, translation tables, labels | bytes, exactly (BOM, line ends, quoting, number text) |
| JSON figures (3.2, 3.5, 3.7) | canonical JSON; numbers as decimal values (`1` = `1.0`), everything else exact |
| exceptions | `python.exception` type mapped to the native error kind by a table in the case (`ValueError` → "refused"); messages not compared |
| `--help` | properties only (3.8) |

No numeric tolerance in F-05's groups: they are calculations on fixed inputs, so equal inputs give equal outputs.
Tolerance belongs to measurements (speed, timing) and is decided by their packages and P-13.

Report: `build/differential/<UTC time>/report.tsv` (case or input id, group, field path, Python value or its hash,
native value or its hash, expected, class) and a short `summary.md` (counts per group and class, the findings
listed first). Exit 0 when no finding, 1 with findings, 2 on an error of the harness.

### 5.6 Concurrency, 32-bit, byte order, budget

- `goldenfile` is plain sequential code; cases are independent, so `t.Parallel()` may be used inside a package.
- Hex inputs are bytes as on the wire; integers in JSON are written as JSON numbers up to 2^53 and as strings
  above (epoch ms fits; an `int64` field above 2^53 is a string), so 32-bit arm and the JSON decoder agree.
- Budget on this PC: the Python suite at `ad3758c` ran in 140-170 s offline; one capture of all groups is expected
  to take minutes, run by the implementer when cases change, not by every gate. On the Pi 4 the cases run inside
  the components' tests; `goldenfile` adds no daemon and no resident memory.
