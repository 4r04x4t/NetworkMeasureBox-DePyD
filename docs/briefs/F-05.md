## 3. Behaviour of the components captured, as intended (Python faults marked)

### 3.1 Configuration load (owner C-01)

- Entry: `load_config(Path)` (`nmb/config.py@ad3758c:851`). With an explicit path the boot-partition copy is not
  consulted (`:856`), so the only inputs are the file, `DEFAULT_CONFIG_TEXT` (`:226-434`) and the environment
  variable `NMB_TELEGRAM_TOKEN` (search hit at `:1088`), which the capture clears. Output for the golden:
  `_ini_dict(_filled(cfg))` (`:1268`, every effective setting as text), plus the log records (level, message) and
  the exception, if any.
- Intended: a bad value is logged and replaced by its default (`:27-36`, roadmap 629); `%` is plain text
  (`interpolation=None`, `:25`; roadmap 640); web port and ping interval clamped (`:841-848`).
- **Python is wrong here (KF-0219):** a syntax error (line without section, duplicate section) raises out of
  `parser.read` (`:905`, only `PermissionError`/`OSError` caught) and stops every service. Correct: the rest of the
  file loads, the bad line is logged.
- **Python is wrong here, defaults** (proposal P9; QB 8 roadmap 596, *Generic First* point 3 roadmap 550): the SMTP
  recipient default is an address at a real, non-reserved domain (`:329`, `:559`); the access point SSID default is
  shared by every box (`:268`, `:510`); the line type defaults to fibre (`:319`, `:547`, also `metrics.py:254`);
  interface names are fixed defaults (`:239-249`, `:457-474`); one box id for every box (`:228`, `:444`); the
  factory Web UI login (`:355`, KF-0056). The cases keep Python's value in `python` and the intended native value
  (empty, generated per device, or detected) in `expected`; the exact native defaults come from F-04's configuration
  contract, so these `expected` fields stay `open` until F-04 is accepted.
- **Python is wrong here, data cap defaults (KF-0294; M-05, also C-01):** the USB link comes with a built-in daily
  limit of 1024 MB (`:693`, and the reader's fallback `:1166`) and the per-link caps default to 0 = no cap
  (`:728-731`), so there is no state "not decided". Correct (owner, 2026-11-11): no default cap number; on a metered
  link speed tests, scheduled or started by a person, wait until the user sets a cap or says unlimited; ping keeps

## 4. Review against the fault register (before any case is used)

Each case file carries a `review` block (5.1). The verdicts:

| Verdict | Meaning | `expected` |
| :--- | :--- | :--- |
| `same` | Python's output is the intended behaviour | equal to `python` |
| `python_wrong` | Python records a known fault; KF id (or proposal id) required | the correct output, different from `python` |
| `open` | it is not known yet (owner question, missing F-04 contract) | absent; the case does not gate a native package until closed |
| `not_comparable` | Python cannot produce it (for example it raises where the native build must load) | the correct output; `python` holds the exception |

Rules (checked by T-REV-1..6):

1. The reviewer goes through every KF entry whose *Package that proves it* or *also* list names the case's owner
   package, and through the proposals of section 12 that touch it; the case lists the ids it was checked against
   (`checked_kf`) and, for each of them, the hash of that entry's defining fields (`register_hashes`, rule 4). The
   register commit the reviewer read is kept as information (`register`), never used as the key.
2. `python_wrong` and `not_comparable` name at least one KF id that exists in the current register, or a proposal
   id `F05-Pnn` from this brief until F-03 gives it a KF id.
3. A `python_wrong` case whose `expected` equals `python` is an error (a fault frozen).
4. **Review key: a hash of the fields that define the fault, per entry (review round 2).** For each id in
   `checked_kf`, `register_hashes[id]` is the SHA-256 (lowercase hex) of these five fields of that entry in
   `KNOWN_PYTHON_FAULTS.md`, and of nothing else: the heading text after `### ` (id and title), *Area*, *What went
   wrong*, *Correct behaviour*, *Package that proves it*. Normalised: the file's line ends to LF; each field's value
   (the text after `- <Field>: `; every field is one line in the register, checked over all 294 entries on the PC,
   section 10) in Unicode NFC, runs of spaces and tabs collapsed to one space, trimmed; then serialised as one line
   per field, `<id>` U+001F `<field name>` U+001F `<value>` LF, in the order heading, Area, What went wrong, Correct
   behaviour, Package that proves it; a missing or repeated field is serialised as the value U+0000 `missing` (and
   T-REV-2 fails it). Not hashed: *Source*, *Python fix commit*, *Spec vector*, *Native test, Go*, *Native test, C*,
   *Status, Go*, *Status, C*, *Status, Python*, so an edit of a status, a test name or a vector path, or of another
   entry, invalidates nothing (T-REV-4 has these as negative cases), while a change of what the fault is, what is
   correct or who proves it invalidates exactly the cases that name that entry. (Keying on the commit failed in
   practice: the first version's `F-03@aea4d1d` was unreachable a few hours later; hashing whole entries, as round 1
   proposed, would have invalidated cases each time a package set its *Status, Go*.)
5. The verifier of a component package re-reads the review of its cases; the reviewer is never the implementer of
   that component.
6. **A stale review turns the case `open`; it fails only the gate of the package that owns the change (orchestrator,
   2026-11-11).** A case is *stale* when (a) a `register_hashes` value differs from the recomputed one, or (b) an
   entry naming the case's owner in *Package that proves it* (or its *also* list) is missing from `checked_kf` (a
   new entry), or (c) its `python` field no longer has the hash the reviewer saw (`review.python_sha256`, rule 7). A
   stale case is run and reported as `open (stale: <reason, ids>)` and does not gate, in every gate, except: in the
   gate of the package that proves the changed or new entry (the first package of its *Package that proves it*
   line) for (a) and (b), and in the gate of the case's owner package for (c), where the stale case fails the gate
   until it is reviewed again. The package under gate is named by the knob `NMB_GATE_PACKAGE` (a package id,
   checked against `^[A-Z][0-9]?-[0-9]{2}[a-z]?$`; an integrator's change of `tools/gate.sh`, section 12); without
   it (the whole-build gate) stale cases are reported, never failing. T-REV-4 and T-REV-6 prove both sides.
7. **The capture never writes `review`.** The reviewer writes `review.python_sha256`, the SHA-256 of the canonical
   JSON of the `python` field as reviewed. A re-capture that changes `python` writes only `python` and `provenance`,
   and marks the change in `provenance.stale` (`{"since": <UTC date>, "previous_python_sha256": <hash>}`); the case
   is then stale by rule 6 (c) until a reviewer writes the new hash. (Round 1 said in 5.3 point 5 that the script
   "resets its verdict to `open`", which contradicted "never writes `review`"; the verdict is now derived, never
   written by the script.)

## 5. Design

### 5.1 Where the files live (decision)

One file per case, so the Python output, the intended output and the review cannot drift apart:

```
tests/golden/README.md                  what a case is, how to capture, review and run
tests/golden/cases/<group>/<case>.json  one case: input reference, python, expected, review, provenance
tests/golden/inputs/<group>/...         made-up inputs: database descriptions (JSON, 5.2), nmb.conf files, hex packets, tool output text, exchanges
tests/golden/capture/                   the Python capture driver, its hook and clock module (also installed as the child's sitecustomize.py), the root build script (runs only on the PC, never in the gate)
tests/golden/groups.tsv                 group, owner package, Go package path of its adapter, Python call list, declared sinks (3.9); read by both scripts
tests/golden/ADAPTER_PROTOCOL.md        the language-neutral differential protocol (5.5): invocation, input, output line, exit codes; version 1
tests/golden/PYREF_SELFTEST.tsv         last result of `tools/pyref.sh selftest` (5.3 point 9)
tests/golden/goldenfile/                Go package: load and validate cases, compare, write the diff report
tests/golden/check_test.go              the review, schema, privacy, register and Phase 0 checks (T-REV, T-CASE, T-P0)
tests/golden/PHASE0.md                  the Phase 0 table of section 7 with each row's package and test name
tools/pyref.sh                          export the Python reference and run the capture in the sandbox (5.3)
tools/differential.sh                   any two or three sides (python, go, c, mixed:<state>) on the same inputs (5.5)
```

Case file (canonical JSON: UTF-8, keys sorted, two-space indent, final newline; byte outputs as strings with an
`encoding` field, binary as lowercase hex):

```json
{
  "id": "csv/speed-skipped-and-formula",
  "group": "csv",
  "owner": "R-02",
  "phase0": ["REQ-RM-1215"],
  "input": {"kind": "call", "db": "inputs/csv/two-rows.json", "call": "export_speedtests_csv", "args": {"start_ms": 0, "end_ms": 1798761600000, "contract_down_mbps": 1000.0}},
  "python": {"output": "timestamp_iso,...\r\n", "encoding": "utf-8", "exception": null, "log": [], "events": []},
  "expected": {"output": "timestamp_iso,...\r\n", "encoding": "utf-8"},
  "review": {"verdict": "same", "kf": [], "checked_kf": ["KF-0034", "KF-0035", "KF-0129"], "register_hashes": {"KF-0034": "<sha256>", "KF-0035": "<sha256>", "KF-0129": "<sha256>"}, "python_sha256": "<sha256 of the python field as reviewed>", "register": "<commit read, information only>", "note": ""},
  "provenance": {"ref": "ad3758c", "python": "3.13.5", "python_pkg": "python3.13 3.13.5-2+deb13u5", "sqlite": "3.46.1", "root": "debian 13, mmdebstrap essential + python3 tzdata mount", "driver": "<commit>", "runs": [["UTC", 0], ["UTC", 1], ["Pacific/Chatham", 0], ["Pacific/Chatham", 1]], "stale": null}
}
```

Input kinds (field `input.kind`; one decoder each, unknown kinds refused):

| Kind | Holds | Used by |
| :--- | :--- | :--- |
| `call` | a function name from the group's fixed list, its arguments, optionally a database (`db`, 5.2), a settings file (`file`), a `/proc/meminfo` text (`meminfo`), the answers of the recording fakes (`sinks`: `which` table, per argument vector an exit code and output) and at most one declared constant change (`patch`: module, name, a path inside `/tmp/case/`) | 3.1-3.7, 3.9 |
| `text` / `bytes` | one parser input: UTF-8 text, or lowercase hex of wire bytes | 3.7, fuzz corpora |
| `command` | a `bin/` command name from a fixed list and its argument vector (no shell) | 3.8 |
| `exchange` | a recorded exchange: an ordered list of frames, each `{"dir": "to_box" or "from_box", "data": <hex>, "note": ""}`, plus the role the code under test plays (`client` or `server`); no time fields at all, timing is excluded by the format; the code under test is fed the frames of the other side in order, and its own frames are compared with the recorded ones frame by frame, in order, byte-exact unless the case lists a field (offset and length, with a reason, for example a random nonce) that is compared by length only | M-06..M-10, S-12, S-13 (REQ-RM-0063, REQ-RM-0141); F-05 itself only has the self-test exchanges of T-DIFF-6 |

`spec/vectors/` (F-07) is seeded from these: when F-07 is built it moves each reviewed case's language-neutral part
(`input`, `expected`) into its vector format with `git mv`-style history and leaves `python`, `review` and
`provenance` in `tests/golden/` (one copy of each fact; F-07 decides the vector schema, F-05 does not pre-empt it).
Until then the component packages read `tests/golden/cases/` through `goldenfile`.

How a component uses it: its own `*_test.go` (inside its folder, work plan 2.2 point 1) registers the group's
adapter and calls `goldenfile.RunCases(t, "<group>")`, which runs each case's input through the adapter and calls
`goldenfile.Compare` (5.5, section 6). So the
cases run in the package's normal test runs A-F of the F-00 gate: amd64, race, two time zones, and arm64 and

### 5.2 Inputs (all made up, reserved values only)

- Databases (decision Q4 of the orchestrator, 2026-11-11: **synthetic only in this package**, written by Python's own
  code; a differential run against the owner's real database is a later P-13 step, on the PC only, with the owner's
  go-ahead, its outputs never committed; note to F-02 in section 12): a fixture is a
  JSON description (`tests/golden/inputs/<group>/<name>.json`: rows as values, no SQL); the capture driver builds the
  file inside the sandbox with the Python reference's own code: `database.connect` and `ensure_schema_upgrades`
  (`nmb/db/database.py@ad3758c:66, 117`), the Python writers where one exists for the table, `rollup_minutes`
  (`:234`), `corrections.apply` and `setup_backfill.apply` (`nmb/db/corrections.py@ad3758c:210`,
  `nmb/db/setup_backfill.py@ad3758c:203`), with `now_ms` given; plain `INSERT` only for rows no Python function
  writes. Each fixture comes in two variants where it matters: with the `kv` marker rows (`data_correction_2026_11_10`,
  `_10b`, `_10c`, `setup_backfill_2026_11_10`) and `speedtest_correction` holding originals, and without them, as an
  older database looks (REQ-CL-0141). The resulting `.db` files are the vectors F-04b asks for
  (`spec/vectors/db/python/*.db`, F-04b draft T-PY-1): F-05 makes them, from `ad3758c`, and from release 2.4.0 once
  its commit is known (section 12); each is recorded with its SHA-256, and a re-capture that gives a different file
  is a finding. **A database is hashed only after it is checkpointed and closed:** the Python connection runs in WAL
  mode (`PRAGMA journal_mode=WAL` from `get_sqlite_pragmas`, `nmb/common/memory.py@ad3758c:109-123`, applied by
  `connect`, `nmb/db/database.py@ad3758c:99-104`), so until a checkpoint the rows are in the `-wal` file, whose bytes
  differ from run to run (its salts are random), while the main file is only the first page. The driver therefore
  runs `PRAGMA wal_checkpoint(TRUNCATE)` on its last connection, requires the first value of the answer to be 0 (not
  busy) and the other two to be equal (every frame copied; with TRUNCATE both read 0, seen on the PC), closes every
  connection, and checks that no `-wal` and no `-shm` file is left before it hashes or copies the file; a fixture
  whose build leaves one fails (T-CAP-15). Tried on the PC (section 10): before the checkpoint the main file was
  4,096 bytes and the WAL hashes of three runs all differed; after checkpoint and close the three main files were
  byte-identical and no `-wal`/`-shm` was left. The same rule holds for every `.db` that a case reads (it gets a copy
  of the closed file) and for the files F-04b receives. Time stamps are fixed epoch milliseconds; addresses from
  192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32 (Python counts these as public on purpose, 3.5,
  which is how a fixture reaches `direct_public`), private ranges only where the case is about private ranges; host names under
  `example.com`/`.net`/`.org`; MACs `02:00:00:...`. A fixture with a public address and no ISP name makes the report
  attempt a GeoIP look-up (`nmb/report/metrics.py@ad3758c:540-552`), so fixtures set an ISP name unless that look-up
  is the behaviour under test (3.2). Large series (a month of ping minutes) come from a seeded generator (Go, in
  `tests/golden/inputs/gen/`) that writes the JSON description at test time (not committed); the Python driver
  builds the file from it the same way. The native side opens the same database file through its reader of a
  Python-format database (C-02, REQ-RM-0208), so one fixture serves both sides; where F-04's native schema differs,
  C-02's migration is part of what the case tests, not a second fixture.
- Settings files: the Phase 0 row "every setting with empty, text, negative, huge and `%` values" is generated from
  the keys of `DEFAULT_CONFIG_TEXT` (one file per key and kind), plus hand-written syntax cases.
- Reused Python test fixtures: only after `privscan` with the private list (KF-0059: the Python test data names
  the owner's ISP and places); a fixture with a hit is rewritten with reserved values, never copied.
- Never in F-05: the real box's database or logs (memory rule; `~/nmb-logs/` is not read), a capture from the box,
  real tokens (decision Q4: the real-database run belongs to P-13, with the owner's go-ahead, and nothing of it is
  committed). Fake tokens are obviously fake and do not match privscan's token patterns.

### 5.3 Capture on the PC (`tools/pyref.sh`)

1. Refuses root (exit 2, KF-0001); refuses a dirty or missing reference commit. `NMB_SRC` (default
   `$HOME/src/NetworkMeasureBox`) and `NMB_PYREF` (default `ad3758c`); exports with
   `git -C "$NMB_SRC" archive "$NMB_PYREF"` into `build/pyref/<commit>/` (ignored), so the working copy of the
   Python repository is never run and gets no `__pycache__`.
2. **The Python that captures is Debian 13's (decision Q6 of the orchestrator, 2026-11-11), in a root built without
   root.** The box runs Debian 13, whose `python3` is 3.13. The I-06 record shows that this Python is **not** in a
   built Debian 13 base: it is in the ISO's package pool (`python3 3.13.5-1`, `python3.13 3.13.5-2+deb13u5`, Priority
   optional), while the three roots A, B and C that I-06 built have no Python interpreter at all
   (`docs/images/debian-13.7.0.md:258-273`; round 1 wrongly said the I-06 "image package list" had it). So
   `tools/pyref.sh root` builds a root of its own the way I-06 built its roots (`:16-25`, `:415-421`):
   `mmdebstrap --mode=unshare --variant=essential --include=python3,tzdata,mount --format=tar trixie -
   http://deb.debian.org/debian`, as the plain user, with the Debian archive keyring taken from the I-06 ISO
   (`pool/main/d/debian-archive-keyring/debian-archive-keyring_2025.1_all.deb`, checked against the ISO's
   `md5sum.txt`, which I-06 verified through the signed `SHA256SUMS`). mmdebstrap's sub-uid cannot enter the home
   folder, so only the keyring is staged in a fresh `mktemp -d /tmp/nmb-F-05.XXXXXX` folder (mode 755), removed
   afterwards; the tar goes to stdout and is unpacked with `tar --no-same-owner` into `build/pyref/root-debian13/`.
   `tzdata` gives `/usr/share/zoneinfo`; `mount` gives `umount`, needed inside the new root (point 3). Tried on the
   PC (section 10): 75 packages, `python3 3.13.5-1`, `python3.13 3.13.5-2+deb13u5`, `libsqlite3-0 3.46.1-7+deb13u2`,
   `tzdata 2026c-0+deb13u1`, 112 s. The package versions (from the root's `dpkg` status) go into every case's
   `provenance`; a root rebuilt with other versions is a new capture, compared like any re-capture. The PC's own
   Python 3.12.3 is used only for trials of the harness, never for a committed `python` field (T-CASE-5 refuses a
   case whose `provenance.python` is not the root's).
3. **A root of its own (allow list of paths).** The driver runs in a new user, mount and network namespace

4. **One fresh interpreter per case and per run (review round 2).** Every case runs four times: `TZ=UTC` and
   `TZ=Pacific/Chatham`, each with `PYTHONHASHSEED=0` and `PYTHONHASHSEED=1`; the four outputs must be byte-identical,
   or the capture fails naming the run that differs (a time-zone or a hash-order fault). Each of the four runs, of
   each case, is a new `python3` process started for that run alone (the driver takes exactly one case and one run
   and exits), and gets a new empty `/tmp/case/` with only that case's inputs: no module state, cache, open
   connection or file can pass from one case or run to the next, so the order of capture cannot matter (T-CAP-13). The
   same holds for differential runs (5.5): one process per input and run. One root is kept for a whole batch; between
   runs the outer stage, which keeps its namespace privileges, unmounts and remounts `/tmp/case/` and copies in the
   next case's inputs; the run itself is the nested user namespace of point 3. The interpreter is started as
   `env -i PATH=/usr/bin LANG=C.UTF-8 COLUMNS=80 HOME=/tmp/home TZ=<zone> PYTHONHASHSEED=<0|1> python3 -s -S -P -B

   every `PYTHON*` variable, `PYTHONHASHSEED` included, so under `-I` each process has a random hash seed (seen on the

   `-s -S -P -B` the same seed gave the same values and seeds 0 and 1 different ones, section 10). With `env -i`
   only the variables listed reach Python, so `-E` is not needed.

### 5.5 Comparison harness (`goldenfile` and `tools/differential.sh`)

Two uses, one comparison code:

- **Gate use (every package):** native output against `expected` of the package's cases. `same`, `python_wrong`
  and `not_comparable` cases gate; `open` cases are run and their result reported, but do not fail. A case of an
  accepted package with no native result fails (no silent skip); a group whose package is not built yet prints
  "not built: N cases".
- **Differential use (PC only, on request and before P-13):** the same input into two or more *sides* (the Python
  driver of 5.3, the Go adapter, later the C adapter of step 2, a mixed state of the migration), also for inputs that
  are not cases: generated databases, settings files, the fuzz corpora of
  the parsers (`testdata/fuzz/<Name>/`, 6B.8 point 4) and recorded exchanges. Each difference is classified:
  - *known*: a case or a rule of the review says Python is wrong there (KF or proposal id given);
  - *finding*: anything else. A finding is written down; it is a fault of one side until shown otherwise, and it
    becomes a case (and a vector for F-07) with a review.

**The native side (adapters).** Each group has one adapter, written by the group's owner package inside its own
folder (work plan 2.2 point 1), in a `_test.go` file, so nothing of it is in a product binary:

```go
// in <component>/golden_test.go
func init() { goldenfile.Register("csv", csvAdapter{}) }
type csvAdapter struct{}
func (csvAdapter) Run(in goldenfile.Input) (goldenfile.Output, error) { ... }   // decodes in.Kind, calls the code
func TestGolden(t *testing.T)       { goldenfile.RunCases(t, "csv") }          // gate use
func TestDifferential(t *testing.T) { goldenfile.RunDifferential(t, "csv") }   // differential use
```

- Gate use: `TestGolden` runs every case of the group through the adapter and calls `Compare`; it runs in F-00's
  runs A-F like any test (`tools/test.sh@2da9473:58-59`: `go test ./...`).
- Differential use: `TestDifferential` does nothing unless the flag `-nmb.diff.in=<dir>` is given (then it reads
  every input file in that folder, of the kinds of 5.1, runs the adapter, and writes one canonical JSON line per
  input with the output or the error kind to `-nmb.diff.out=<file>`); without the flag it calls `t.Skip("no
  differential inputs")`, which is not a gating case.
- Discovery: `tests/golden/groups.tsv` (group, owner, Go package path, Python call list, declared sinks) is F-05's
  file. For each group, `tools/differential.sh` runs `go test -list '^TestDifferential$' <path>`: no match means
  "not built: group <g>" (counted, no failure); a match runs `go test -count=1 -run '^TestDifferential$' <path> -args
  -nmb.diff.in=<dir> -nmb.diff.out=<file>` inside F-00's `nmb_offline`; the Python side gets the same folder from
  `tools/pyref.sh run --group <g> --inputs <dir> --out <file>` (5.3: one fresh interpreter per input and run, four
  runs per input that must agree). The script then compares the files line by line with `goldenfile`'s comparison
  (one comparison code for both uses), and writes the report below.

**The adapter protocol (language-neutral; REQ-RM-1465, REQ-RM-1467; review round 2).** The differential input and
output are not Go-specific: `tests/golden/ADAPTER_PROTOCOL.md` (version 1) defines them, so that the Go adapter, the
Python driver, the C adapter of step 2 and a mixed Python-plus-native state are compared by the same tool. An
*adapter* is anything that obeys:

- **Invocation:** `<adapter> --protocol 1 --group <g> --in <dir> --out <file>`, no other arguments, no network, no
  writes outside `<file>` and its own temporary folder; for the Go side, `tools/differential.sh` wraps the `go test
  -run TestDifferential` call above into this form; a C adapter (X2-01) is a plain executable built for the target
  and run on the PC or under `qemu-*-static`; a mixed state is a launcher script of P-13 that brings the state up
  (F-06 namespaces or a guest), feeds the inputs through the components that are native in that state, and answers
  in this form.
- **Input:** every `*.json` file in `<dir>`, each one input object of 5.1 (`kind` and its fields; paths relative to
  `tests/golden/inputs/`), read only; inputs are processed in byte order of their file names, each on its own (no
  state from one input may reach the next; a side that cannot guarantee it in-process starts a process per input, as
  the Python side does).
- **Output:** UTF-8, one line per input in the same order, each line a canonical JSON object (keys sorted, no
  insignificant white space, strings with only `"`, `\` and control characters escaped, integers as JSON integers up
  to 2^53 and as decimal strings above, other numbers in their shortest round-trip form, no NaN or infinity) with
  the keys `id` (the input file name), `side` (`python`, `go`, `c`, `mixed:<state_id>`, the state ids of F-04b's
  `spec/db/bridge.json`), `output` (the fields of `goldenfile.Output` of section 6, bytes as lowercase hex),
  `error_kind` (null, or one of the error kinds of the group's table), `log` and `events`.
- **Exit status:** 0 when every input has its line (an error kind is a result, not a failure of the adapter), 2 when
  the adapter could not run (then the file is not used); a missing line, a line for an unknown input, a second line
  for one input, or a line that is not canonical makes `differential.sh` stop with 2.
- **Comparison:** `differential.sh --sides python,go[,c|mixed:<id>]` compares each pair of sides on each input with
  `goldenfile.Compare` and the normalisation table below, and classifies each difference as *known* (a case or review
  rule names the fault of one side) or *finding*. The report has one column per side.

T-DIFF-8 runs a stub adapter written as a POSIX shell script (not Go) through the protocol, as a third side next
to the Python driver and the Go adapter of the self-test group, and a stub `mixed:<id>` side; a wrong line from the
stub is a finding naming that side.
- An `exchange` input is run by the adapter of the protocol's package, which plays its role against the recorded
  frames of the other side (5.1); the Python side of an exchange is the recording itself (made by the protocol
  package from the Python version talking to the real peer, or from the peer's own reference implementation), so
  the comparison is native against recorded. F-05 delivers the kind, its decoder and comparison, and T-DIFF-6 with a
  toy echo protocol; the recordings and their adapters belong to M-06..M-10, S-12 and S-13.

Normalisation, stated per output kind and never wider than this:

| Output kind | Compared as |
| :--- | :--- |
| CSV, `nmb-cli` JSON, translation tables, labels | bytes, exactly (BOM, line ends, quoting, number text) |
| JSON figures (3.2, 3.5, 3.7) | canonical JSON; numbers as decimal values (`1` = `1.0`), everything else exact |
| exceptions | `python.exception` type mapped to the native error kind by a table in the case (`ValueError` → "refused"); messages not compared |
| exchanges | frame by frame in order, bytes exact except the fields a case lists (compared by length); frame count and direction exact |
| `--help` | properties only (3.8) |
| recorded calls (3.9) | argument vectors and stdin text exactly, in order; the firewall's `expected` is F-04d's canonical text, compared byte for byte with the native renderer's output |

No numeric tolerance in F-05's groups: they are calculations on fixed inputs, so equal inputs give equal outputs.
Tolerance belongs to measurements (speed, timing) and is decided by their packages and P-13.

Report: `build/differential/<UTC time>/report.tsv` (case or input id, group, field path, one column per side with
the value or its hash, expected, class) and a short `summary.md` (counts per group and class, the findings
listed first). Exit 0 when no finding, 1 with findings, 2 on an error of the harness.

### 5.6 Concurrency, 32-bit, byte order, budget

- `goldenfile` is plain sequential code; cases are independent, so `t.Parallel()` may be used inside a package.
- Hex inputs are bytes as on the wire; integers in JSON are written as JSON numbers up to 2^53 and as strings
  above (epoch ms fits; an `int64` field above 2^53 is a string), so 32-bit arm and the JSON decoder agree.
- Budget on this PC: the Python suite at `ad3758c` ran in 140-170 s offline. A capture run is one fresh process in
  the root (5.3 point 4); measured in review round 2 (section 10, root setup included): about 0.35 s for a small
  case, about 1.0 s with the heavy imports (`nmb.web.i18n` and the bot texts), about 32 MiB peak RSS. Four runs per
  case, so about 1.5-4 s per case; for 1,000 cases about 25-70 minutes on one thread, about half with two parallel
  roots (2.2 point 9 leaves room for two at 32 MiB each). Keeping one root per batch and starting only the
  interpreter per run (5.3 point 4) removes most of the setup time. It is run by the implementer when cases change,
  not by every gate. On the Pi 4 the cases run inside
  the components' tests; `goldenfile` adds no daemon and no resident memory.

## 12. Questions and reports

### Decided by the orchestrator (Orchestrator, 2026-11-11)

The questions Q1-Q6 of the earlier versions were decided by the orchestrator on 2026-11-11 and are no longer on the
owner's list. Each decision is written where it applies; the summary:

- **Q1 Statistics (Orchestrator, 2026-11-11).** Python's definitions are faults (QB 6). The native build uses the
  standard definitions, in this brief and as vectors: the median of an even count is the mean of the two middle
  values; p95 by the nearest-rank method on the sorted sample (rank `ceil(0.95 n)`, the 19th of 20 values); the
  minimum and maximum latency come from the stored minute minima and maxima, not from minute averages. Golden cases
  record Python's output and are `python_wrong` F05-P7 (3.2).
- **Q2 A measured 0 bit/s (Orchestrator, 2026-11-11).** A value from a test that completed is a measurement, 0
  included; a skipped or failed test has no value (NULL). The report must not treat a stored 0 from a completed test as
  not measured; the CSV must not write 0 for a skipped one. F05-P6 (3.2).
- **Q3 Number text in the exports (Orchestrator, 2026-11-11).** Python's text forms (`0.0`, `912.35`) are kept for
  CSV compatibility, specified exactly: round half away from zero to the stated decimals (on the shortest
  round-trip form of the value, 3.4), with the places where Python's float formatting differs named; Python's
  "2.5 ms -> 2 ms" is a fault, F05-P15 (3.4).
- **Q4 Real databases as differential inputs (Orchestrator, 2026-11-11).** Synthetic only in this package. A
  differential run against the owner's real database is a later P-13 step, on the PC only, with the owner's
  go-ahead, its outputs never committed (5.2; note to F-02 below).
- **Q5 Schedule shorthand words (Orchestrator, 2026-11-11).** The native configuration accepts only the
  language-neutral forms (cron and the `10s`/`5m` units); English or Hungarian shorthand found in an existing
  Python `nmb.conf` is converted to the cron form at migration with a logged notice; no country-tied words in the
  parser (QB 9). F05-P16 (3.7).
- **Q6 Python version of the captures (Orchestrator, 2026-11-11).** Captures run with Debian 13's `python3` (3.13,
  the version on the box) inside an `mmdebstrap` root built without root, as I-06 shows; the PC's 3.12.3 only for
  trials (5.3 point 2).
