### 3.3 How the figures are computed (and what each one means)

- **Throughput samples** `s_k = 8 · Δbytes / (Δt · 10⁶)` Mbit/s every 0.5 s over all streams, from `Mono` (PY 361).
  Download bytes are counted when read by the engine; **upload bytes are counted when the peer has acknowledged
  them**: per stream `delivered = written − SIOCOUTQ` (the ioctl returns "not sent + not acked",
  `linux/sockios.h` comment; the tcp(7) man page says only "unsent", the kernel's own header is taken, S-12) read at
  every sample. **Python does** count upload bytes when they are handed to the socket (PY 281-285); **correct is**
  delivered bytes (F-M07-4).
- **Mean** = bytes inside [3 s, 15 s] · 8 / 12 s (PY 369).
- **Stable speed** (the value stored as `down_bps`/`up_bps`): from the samples after the warm-up, `ref` = median of
  their second half; start at the first sample ≥ 0.9 · `ref`; mean from there to the end (PY 321-330, REQ-RM-0152,
  REQ-RE-0080). If there are no samples after the warm-up the direction is **not measured** (NULL). **Python does**
  fall back whenever the stable figure is falsy, that is `None` (no samples after sample 6, PY 326-327, 372) **or**
  `0.0` (`stable or mean`, PY 409-410), to `mean_mbps`, which is not a mean over the samples but the window bytes
  × 8 / 12 s (`meter.total`, bytes counted only inside [3 s, 15 s], PY 223, 251, 369); so a direction with no
  samples after the warm-up can still be stored with the window-bytes mean, and the direction counts as failed only
  when that mean is 0 too (PY 443). **Correct is**: no post-warm-up samples → NULL with the reason `no_samples`†, never
  the window mean in its place; a stable figure of 0.0 is a measured 0 only when bytes were counted, else NULL. The
  stable rule is NMB's reconstruction of "the mean once the speed settles" (BLOG: rolling average after the ramp-up,
  dynamic stop); Fast.com's own algorithm is not published, so the manual says "computed like Fast.com", not
  "Fast.com's result" (3.4).
- **Peak** = max sample; **per-server Mbit/s** = that server's bytes in the window / 12 s (PY 420-421).
- **Unloaded latency** (`ping_us`) = min over all targets' 6 samples (PY 401-402); it is an **HTTP request round trip**
  (request, server work, first and last byte of a tiny body), not ICMP; the manual says so.
- **Jitter** (`jitter_us`) = mean absolute difference of successive samples of the closest target (PY 403-405): NMB's
  own figure (Fast.com shows none), from 6 samples; NULL with fewer than 2 samples.
- **Loaded latency** (`down_loaded_lat_ms`, `up_loaded_lat_ms`) = median of the probe samples inside the window of
  that direction (PY 411-412). A probe that times out (native timeout 2 s†, inside the window; Python's is the
  socket's 10 s of `_connect`, PY 174, 304) enters the median as the
  timeout value, a lower bound; `raw_json.<direction>.probe_timeouts` stores their number; when at least one timeout
  entered the median, the loaded latency and the grade derived from it are marked "at least"
  (`raw_json.bufferbloat_at_least = true`, shown as "≥" by the readers; Orchestrator, 2026-11-11, D6). **Python does**
  drop timed-out probes (PY 301-318), which makes a bad line look better (F-M07-5).
- **Bufferbloat** grade and delta: the shared function (R-01/M-04; Python's `calculate_bufferbloat`,
  `ookla.py@ad3758c:60-95`) from the idle latency and only the directions with loaded samples (KF-0125,
  REQ-CL-0196).
- **Colo** = the third dash-separated part of the server name (PY 470), upper-cased, only when the name has the
  Open Connect form; otherwise NULL.

### 3.4 What is not measured (said in the manual and never filled)

  adaptive connections and duration, BLOG, PAGE); the row is "NMB's measurement against Fast.com's servers"

- **Other:** DNS time, TLS handshake (on plain HTTP), the second address family, per-hop delay.

### 3.6 Transport: plain HTTP or TLS (Q-27, decided as a measurement)

The register settled Q-27: the M-07 analyst measures both on the same box and line; TLS where it reaches the line
rate on the Pi 4, plain HTTP where the comparison shows TLS limits it (REQ-CL-0075, `QUESTIONS.md` Q-27). This early
brief cannot do it (no native engine yet), so the engine supports **both** (`https=true|false` in the API call,
port 443 or 80) and the measurement is the implementer's step on the Pi 4 under work plan section 7 point 5
(Blocked B4). Facts for it:

- The Pi 4's Cortex-A72 has no AES and PMULL instructions (OpenWrt target `aarch64_cortex-a72`, image record); Go
  1.27.4's `crypto/tls` then offers ChaCha20-Poly1305 **first** in its ClientHello (`defaultCipherSuitesTLS13NoAES`,
  defined at `crypto/tls/defaults.go:114`, appended at `handshake_client.go:139`; the TLS 1.2 order
  `cipherSuitesPreferenceOrderNoAES` at `cipher_suites.go:315`; read locally), but the **server** chooses; which suite
  an Open Connect server picks is not known (to record in the measurement).
- Python's figures, as its source gives them: with TLS "77-88 % of the CPU at 910 Mbps", with plain HTTP "50-56 %"
  (PY 46-48); the source does not say whether that is one core or the whole CPU (four cores), so the measurement
  records both (per-core and total, from M-04's CPU sampler). They are Python's (OpenSSL in `http.client`), not Go's;
  QB 4 asks the native build to do better.
- Plain HTTP has a cost besides speed: a transparent proxy or cache on the path could answer instead of the server
  and nothing proves who sent the bytes. The row records `transport`; the manual says it.

### 3.7 Identity and headers

- Every request sends `User-Agent` from C-05: `NetworkMeasureBox/<version> (speed)`† by default, the owner's custom
  value when set (then `user_agent_custom = 1`). No browser agent, preset or random value (owner, 2026-11-11; C-05
  3.4; Owner, 2026-11-11, D1). **Python does** fall back to a hard-coded Chrome agent (PY 62-67, C-05 NF-1).
- **Python does** send `Origin: https://fast.com` and `Referer: https://fast.com/` on every request (PY 70-71),
  claiming the requests come from Fast.com's own page; **correct is** no `Origin`, no `Referer` and no other browser
  header (`Sec-*`, `Accept-Language`, browser `Accept` strings) (Owner, 2026-11-11, D1; Orchestrator, 2026-11-11,
  D5; REQ-CT-0007, "no borrowed identity"). If the API then refuses, that is a refusal (3.10): the engine pauses and
  never adds them back (F-M07-1).
- The only other headers are functional ones the protocol needs: `Accept-Encoding: identity` on transfers (no
  compression asked; `Transport.DisableCompression`), `Content-Type: application/octet-stream` and `Content-Length`
  on uploads (as PY 273-274), `Host` (set by `net/http`). A test (T-M07-11) checks that no other header is sent.

### 3.8 Data use per run (for M-05)

Bytes per run ≈ (R_down + R_up) · 15 s / 8, plus small parts: the latency phase (5 × 8 tiny requests), the loaded
probe (≈ 75 tiny requests), the API answer (a few KiB) and, once a day while the token is cached, the page and the
script (well under 1 MiB† each). All 15 s move data, the 3 s warm-up included. Examples (generic): 100/100 Mbit/s ≈
375 MB; 1000/1000 Mbit/s ≈ 3.75 GB; the README's figure for its gigabit line, about 2.2 GB per run, fits this
(REQ-RE-0082). The schedule's frequency is the user's (Owner, 2026-11-11, D2: any interval; only data caps and the
refusal pause limit it; Fast.com has no hourly rule of its own): at the generic example of one run an hour that is
24 runs, about 9 GB a day at 100/100 and about 90 GB at 1000/1000; at a few minutes' interval (the owner's own
schedule, TESTING@ad3758c:387) many times that. The manual states the per-run figure next to the interval setting.

- **Overshoot after the window** (not in the formula above): when a window ends, data already sent by the servers
  but not yet read (in the receive buffers and in flight, about one bandwidth-delay product per stream, at most the
  receive buffer each) still reaches the interface and counts against a cap, though the engine never reads it;
  upload data written but not yet sent is sent after the window unless the socket is closed abortively. Bound per
  direction: 16 streams × the maximum socket buffer (`net.ipv4.tcp_rmem` / `tcp_wmem` third field, read at run time
  through C-09; the kernel sizes it from the memory, for example `tcp_rmem` max 14,733,888 and `tcp_wmem` max
4,194,304 bytes read on the development PC's kernel 6.18 on 2026-11-11, so up to about 225 MiB down and 64 MiB up
there; the Pi 4's own values are read on the box†) plus the probe; in practice the bandwidth-delay product is far
smaller (1 Gbit/s × 20 ms ≈ 2.4 MiB for all streams together). To keep it small the
  engine closes upload sockets at the window's end with `SO_LINGER` 0 (unsent data dropped)† and closes download
  sockets at once. The same overshoot follows a budget stop and a cancel. M-05 is told this bound with the estimate.
- The engine reports `bytes_down`, `bytes_up` (its own counts of every byte read or acknowledged from the first
  request to the close, warm-up included); M-05 counts the interface as the authority (KF-0230).
- **Budget**: the engine takes a byte budget from M-05 (expected interface, section 6) and stops a direction when the
  run's bytes reach it; that run is aborted with reason `data_budget` and no values (an aborted run is treated as
  skipped: no partial result is saved, Phase 0 gate table `@ad3758c:650-656`; roadmap@bb0a553:691). With no budget
  (unlimited) nothing changes. Whether M-05 hands a budget to a person-started run is M-04's and M-05's (Owner,
  2026-11-11, D2: a person's test is never held back except by a refusal pause; B10).
- **Estimate before a run** (for a cap check): `(last stable down + last stable up of this engine on this link) ·
  15 s / 8 · 1.1 + 2 · overshoot bound`†, or, without a previous result, M-05's own rule (Blocked B2). The factor 1.1
  covers what the interface counts beyond the payload (TCP/IP and HTTP headers, about 3 % at a 1500-byte MTU, the
  ACK stream of the opposite direction, retransmits) and the gap between the stable figure and the 15 s average; it
  does **not** cover the overshoot, which is the separate term.
- Metered link without a cap decision: the run waits (M-05/M-04; KF-0294); not the engine's decision.

### 3.9 Server choice (Quality Bar 9)

The box does not choose servers and holds no list: Fast.com's API names up to five Open Connect servers for the
address it sees (BLOG: distance, load, different clusters). So the choice follows the box's location and line by
design, in every country. Conditions that keep it so:

- The API call leaves through the **measuring link** (bound dialer), so the API sees that link's public address.
  KF-0231 as the register words it: bind before connect; without an address the engine leaves through the default
  route **and the row describes that link** (roadmap@ad3758c:452). **Python does** bind only the source address and
  only when the link has one (PY 76, 175, 185), never the device; without an address it runs unbound through the
  default route (that part is the intended behaviour) **but the row still names the asked interface**
  (`bound_iface=interface`, PY 392, 395, 471; `runner.py@ad3758c:354-357`), which is the fault. **Correct is**: every
  socket bound by F-04d 4.1.7's dialer before connect; when unbound, the row's `bound_iface`/`bound_ip` are the link
  and address actually used (3.5, from `LocalAddr`).
- Address family: with a bound IPv4 (IPv6) source only targets of that family are used; the row's `ip_version` says

- No country, city or ISP appears in code or tests (QB 8, 9; KF-0059): the label parser accepts any three-letter
  site code; tests use `example.net`-style names and documentation addresses.

authentication credentials", which a token kept 24 h by the box itself can become; fetching the token again from the
page is what the page itself does on every visit, so it is no workaround. 403 is "understood the request but refuses
to fulfill it" (RFC 9110 15.5.4); the RFC lets a client repeat it "with new or different credentials" but also
says it "might be forbidden for reasons unrelated to the credentials", and the orchestrator's rule (D3) takes the
cautious reading: a 403 is a refusal, with no second token. Python's
comment says the token "is the same for every visitor and has not changed in years" (PY 42), so a stale token should
be rare. Which status the API gives for a stale token is not known (no recorded exchange, B5); if B5 shows it is 403,
the orchestrator revisits this row (B11).

## 7. Design

### 7.1 Packages and types

- `internal/speed/fastcom`: `Engine` (implements M-04's interface); `discover.go` (page, script, token cache, API,
  target validation); `latency.go` (P4, probe); `transfer.go` (workers, meter, sampler); `result.go` (stable speed,
  `raw_json`, columns). Pure functions (`stableMbps`, `parseLabel`, `parseAPI`, `extractToken`, `validateTarget`) are
  separate and fuzzed.
- If package M-17 (shared HTTP transfer core, `PACKAGE_CHANGES.md` line 86) is accepted, the worker pool, meter,
  bound transport and acked-byte counting move there and M-07 keeps discovery, latency and the result.
- HTTP: `net/http` with one `http.Transport` per stream (`DialContext` = the bound dialer, `DisableCompression`,
  `ForceAttemptHTTP2 = false`, `MaxIdleConnsPerHost = 1`, `MaxResponseHeaderBytes = 16 KiB`†, TLS verification on,
  `ServerName` from the target's name). Download bodies read with a 64 KiB static buffer (`Body.Read` reads directly
  into a buffer at least as large as `bufio`'s). Upload bodies from an `io.Reader` that generates random bytes
  (ChaCha8 seeded from `crypto/rand` per run†) and stops at the window; the connection is recorded at dial time so
  `SIOCOUTQ` can be read through `SyscallConn().Control`.

### 7.2 Concurrency

16 worker goroutines per direction, 1 probe, 1 sampler, all under one `context` derived from the run's; each socket
is closed by `context.AfterFunc(ctx, conn.Close)`; a `sync.WaitGroup` is waited for before `Run` returns (F-M07-6).
Counters are `atomic.Uint64` per stream (read by the sampler without locks). Per-target error lists are bounded (≤ 5
kept) under a mutex. The race detector runs on every test (gate).

### 7.3 Detected at run time

Address family of the link; whether `SIOCOUTQ` works (a failure → upload counted at the socket and
`raw_json.upload.count_method = "written"`, marked, never silent)†; the transport chosen (config or Q-27 result);
AES hardware (read from `/proc/cpuinfo` features through C-09) only to record it with the measurement.

### 7.4 Byte order and 32-bit

No binary protocol (HTTP and JSON text). `SIOCOUTQ` returns a C `int` on every Linux architecture. Byte counters are
`atomic.Uint64` (aligned on 32-bit ARM and MIPS by the type). Durations from `Mono`.

### 7.5 Security and privilege

No privilege of its own; `SO_BINDTODEVICE` needs `CAP_NET_RAW`, held by M-04's dialer (F-04d 4.1.7, P-04). Runs in
the standard service sandbox of 6B.5 (own engine; network access to the internet only, no file writes).

### 7.6 Logging

Structured events (C-03): `speed.fastcom.discover` (token source, target count, transport), per-target errors at
`debug`, refusals at `warn`. Never the token, the request queries or the client address in the log.

### 7.7 Resource budget on the Pi 4 (estimates †, to be measured)

Memory: 32 × 64 KiB read buffers = 2 MiB, upload generator state per stream small, `raw_json` < 16 KiB, goroutine
stacks < 1 MiB: under 8 MiB† during a run. CPU: at line rate the target is below Python's plain-HTTP figure and, over
TLS, a result at line rate (QB 4); measured with M-04's CPU sampler and recorded in `docs/TESTING.md`.

| :--- | :--- |
