## 2. Method

1. **Seed.** The 47 faults of the roadmap register (610-619), in its order and with "What went wrong" copied as
   written, as the F-00 brief fixes. Each got its correct behaviour from the CHANGELOG entry that fixed it (the
   CHANGELOG states the behaviour after the fix), from roadmap 4.29 for the setup entries, and from the rules from
   fixes; its fix commit from the git history and the private fix-progress lists.
2. **New entries.** One per fault, from: the Quality Bar examples (583, 592, 604); the Phase 0 table and the rules
   from fixes (each rule names a fault that happened); every *Fixed* and *Security* bullet of the CHANGELOG (trivially
   related bullets grouped, none dropped); the "after a fix" rows of `TESTING.md`; *To fix* and the software-caused
   *Known limits*; every item of the private notes.
3. **Status.** "fixed" only where a source records the fix (commit given when the subject or body names it,
   otherwise "not recorded in the source"); "open" where the newest source says so, or where the Python code at
   `ad3758c` shows it (marked "source analysis"). Register line 617 says "being fixed"; the CHANGELOG and the private
   data-quality list record those fixes as live on 2026-11-10, so KF-0030 to KF-0040 are "fixed" with that note. This
   differs from the seed of the F-00 brief (section 6, line 492: "line 617 says being fixed"); the orchestrator takes
   this file at merge. A fault with no fix has "Python fix commit: not recorded in the source; note: not fixed"; every
   note follows the value after `; note: ` (register rules), so the values stay those of the F-00 format.
   Register line 604 lists the Hungarian-only dossier label as a fault; `git log -S` shows it was removed in
   `da88eb1`, so KF-0058 is "fixed".
4. **Open security holes** of the private audit are recorded only by category (KF-0267 to KF-0282): the category,
   the generic correct behaviour from Quality Bar 7 (roadmap 587-591) and the rules from fixes (679-682), the private
   item numbers. No place, input or way of use, and no clause written against one private item: after review round 1
   every category holds several items, the single-item categories of the first version were folded into broader ones
   (the ids kept, their titles changed before the register was ever merged), and the specific requirements stay in
   the private audit, where the analyst of the proving package reads the listed items. Holes that are fixed and
   public in the CHANGELOG are described as the CHANGELOG does. Open faults that are not security holes are
   described by their behaviour, citing public Python code lines where the source analysis confirmed them, never the
   private notes' file and line details; an open fault that an outside party could trigger is described by its
   effect only, without trigger or code lines. Since review round 3 a category entry names only its proving
   package; the "also" packages are in the private package list of 2026-11-11.
5. **Packages.** The package whose component the fault lives in proves it; packages that only show or store the
   value are "also". `S-02`/`U-02` stand for the API-area and page packages the integrator splits.
6. **No personal or site data:** the owner's ISP, devices, addresses and account names are written generically; a
   scan of the register for them (and for the factory password and the other device's firmware number) found none.
7. **Review round 1 (2026-11-11).** The verifier's 14 findings were each checked against the source; the result is
   in section 12.
8. **Review round 2 (2026-11-11).** The verifier's 10 findings were each checked against the source; the result is
   in section 13. Sections 3, 4 and 6a were regenerated from the register by a script after the changes.
9. **Review round 3 and the owner's answers (2026-11-11).** The owner answered questions 1 to 5 and decided the
   trust of the uplink network; each answer is written into the entries it decides as "Owner, 2026-11-11: ...".
   The verifier's 14 findings were each checked against the source. Both are in section 14. Sections 3, 4 and 6a
   were regenerated from the register by a script after the changes.
