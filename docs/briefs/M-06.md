## 3. Source analysis

### 3.1 The Python engine (`nmb/speed/cloudflare.py@ad3758c`)

Entry point `execute_cloudflare_speedtest(interface, bind_ip)` (422), called only by the runner
(`runner.py@ad3758c:159-163`). Sequence and constants:

| Step | What Python does | Lines |
| :--- | :--- | :--- |
| 0 | module globals `_bound_source_ip`, `_peer_ips` set for the run | 41-42, 424-426 |
| 1 metadata | `GET /__down?bytes=0` through `urllib` (own connection), reads headers `cf-meta-ip`/`CF-Connecting-IP`, `colo`/`cf-meta-colo`, `city`, `country`, `asn`, `latitude`, `longitude`, `postalCode`, `timezone`; any error is logged and ignored | 206-222 |
| 2 idle latency | `getaddrinfo` once, then 5 TCP handshakes to `speed.cloudflare.com:443` (each `create_connection` with the host name), 80 ms apart; median; jitter = mean of absolute consecutive differences, `None` with one sample | 234-261, 436 |
| 3 capacity | `/sys/class/net/<if>/speed` if > 0 | 397-405 |

### 3.4 RECORD_LAYER_FAILURE: what the message is

OpenSSL 3.2 and later wrap record-layer failures: `ossl_statem_fatal(s, al, SSL_R_RECORD_LAYER_FAILURE, NULL)`
when the record-layer method returns fatal with an alert (OpenSSL 3.5.4 `rec_layer_s3.c:524-530`), so the real
reason (for example a record that fails its integrity check, an oversized record, a decryption failure) is an
earlier entry of OpenSSL's error queue that Python's `ssl` message does not show. Python's string match
(`cloudflare.py@ad3758c:418`) therefore lumps every such cause together. Go's `crypto/tls` returns the specific
cause (`tls: bad record MAC` alert, `RecordHeaderError` with the five header bytes, `io.ErrUnexpectedEOF`, a reset
from the kernel). This is what makes the comparison of section 6 informative. What the Pi's drops are is not known
yet; the roadmap's list of what was ruled out (GRO, receive checksums, read size, the latency probe, TLS version) is
kept (KF-0286).

### 3.5 Component choice

Go standard library only for the protocol (`net/http` with HTTP/1 only, `crypto/tls`, `net`), plus
`golang.org/x/sys/unix` for `TCP_INFO` (delivered bytes, retransmits, RTT at a drop; BSD-3-Clause, fits the rule of
`DEPENDENCIES.md`; pinned and `govulncheck`-clean at implementation; row added then by the integrator). Without it
the same can be read through `syscall.RawConn.Control` and a raw `getsockopt`; recommended: `x/sys` (typed struct,
correct on 32-bit). No code is taken from the MIT Cloudflare engine (it is a browser library in TypeScript); it is
cited as a source. Nothing is read or taken from the GPL-3.0 `cloudflare-speed-cli` (clean room; its licence would
need the owner, `DEPENDENCIES.md`).

## 4. Behaviour as intended (with the Python faults marked)

### 4.1 Server choice and metadata

- **No server list.** The server is the Cloudflare edge that the line's routing reaches for `speed.cloudflare.com`
  (anycast); the box neither picks nor pins one. Nothing in the code names a colo, an address or a country
  (QB8, QB9, REQ-RM-1112). The name is resolved once per run through the measured link's resolver (F-04d 4.1.6).
- **Family and address (M06-R1).** One address is chosen from the answer: the family of the run follows the
  runner's request (`ip_version` 4 or 6), else the family of the source address the runner gives, else (no
  request, no source address) IPv4 when the link has a usable IPv4 address, else IPv6 when it has only a usable
  IPv6 address (an IPv6-only link). With no usable address of either family the engine does not guess: the run
  fails with `reason_code` `no_source_address` (B3); the runner resolves an addressless link to the default
  route's link and address before it calls the engine (4.7, roadmap 4.29), so this is a fault of the call. If the
  resolver's answer has no address of the run's family, the run fails `dns_failed` with the family in raw; it never
  falls over to the other family. Every connection of the run, transfers and latency probes, goes to that one
  address. **Python does** resolve per connection
  (`cloudflare.py@ad3758c:228, 238`), so one run can mix edge addresses (and families, when it has no source
  address), and takes its metadata from a separate `urllib` connection (210); **correct is** one address per run and
  metadata from the measured connection itself.
  *Which family Python used (evidence, for the comparison of REQ-RM-1038):* the engine passes the runner's source
  address to every `create_connection` (227-228, 236-238). CPython's `create_connection` tries each `getaddrinfo`
  answer in turn and goes on to the next when `bind` fails, and an IPv4 source address cannot be bound on an IPv6
  socket, so with an IPv4 source the run is IPv4 whatever the resolver's order. The runner's source address is IPv4
  whenever the link has one: `_usable_address` takes IPv4 first (`interfaces.py@ad3758c:445-450`); the other paths
  take the first entry of `ip -j addr` (212-232, 434-436, 472-473), where iproute2 lists `inet` before `inet6`.
  Only without a source address (the warning paths 487, 497, 504: a link without an address) did glibc's RFC 6724
  order decide, which puts a global IPv6 destination first on a dual-stack host. As far as the code shows, the
  Python history is IPv4 on every link that has an IPv4 address. The stored `server_ip` values on the box were not
  checked (key login from the development PC was refused on 2026-11-11 and nothing else was tried); T-M06-31 checks
  the family of the Python rows before the comparison of 9.4. The last fallback (IPv4 without a source address) is
  a **choice** that matches that history, not a copy of Python's behaviour in that case.
- **Metadata** comes from the first `GET /__down?bytes=0` on stream 1 after its TLS handshake (it also warms the
  connection): `colo` (≤ 16, `[A-Z]{3,4}` checked; anything else is "unknown"), the client address `cf-meta-ip`
  (parsed as an address; stored only when global, split into `client_ip` and `client_ipv6` by C-05's rule), `asn`
  (digits ≤ 10), `city` and `country` (≤ 64, printable, raw record only). `cf-ray`'s suffix is a cross-check.
  If `colo` is missing, one `GET /cdn-cgi/trace` on the same connection (lines `key=value`, ≤ 4 KiB read, keys
  `colo`, `ip` used). Latitude, longitude, postal code and time zone are not stored (M06-R11).
- **Row fields:** `server_name` "Cloudflare Edge (<colo>)" or "Cloudflare Edge"; `server_location` "Cloudflare
  <colo>" or NULL (REQ-CL-0197); `server_host` "speed.cloudflare.com"; `colo`; `server_ip` = the run's address
  (REQ-CL-0007); `server_id` NULL; `result_url` NULL (REQ-RM-1157, REQ-CL-0349: Cloudflare gives no result page).

### 4.2 Transfers (phases, timings, streams)

Constants (named, in `spec/` per 6B.8): `streams = 4`, `phase = 8 s`, `warmup = 2 s` (window 6 s), `idle_samples = 20`, `idle_interval = 80 ms`,
`probe_interval = 500 ms`,
`down_request = 100 000 000` bytes, `up_request = 25 000 000` bytes, `connect_timeout = 5 s`,
`stall_timeout = 5 s` (no byte read or acknowledged), `reconnect_pause = 200 ms`, `reconnects_per_stream = 2`.
The Python values are kept where they are intended (REQ-CL-0430, REQ-RE-0077) so the native rate is comparable
(REQ-RM-1038); Python's 15 s sequential connect (225-231, 369-373) becomes a parallel connect with 5 s.

1. **Prepare (not timed):** resolve; open 4 TLS connections in parallel, bound to the link (4.7), HTTP/1.1 only
   (`Transport.Protocols` with HTTP/1 only, ALPN `http/1.1`; one TCP connection per stream, REQ-RM-0026, REQ-PP-0081
   "pre-warmed keep-alive HTTP/1.1"). Fewer than 4 established within 5 s: that phase is not run (a figure from fewer
   streams would be a lower speed, not the method's), its direction failed `connect_failed`, and the run goes on to
   the other phase (status rule of 4.5, D5); none in either phase: failed `connect_failed`.
2. **Idle latency** (4.3), on the prepared address, before any load.
3. **Download phase:** all streams start together at `t0` (monotonic); each loops `GET /__down?bytes=100000000`
   on its keep-alive connection and reads into its own fixed 64 KiB buffer (REQ-PP-0084); a byte counts when its
   read returns inside `[t0+2 s, t0+8 s]` (Python's meter, 285-288, kept). What is counted are HTTP body bytes
   (the plaintext `Response.Body` returns; status line and headers are not body). At `t0+8 s` every connection's
   deadline fires, the readers stop at once and the connections are closed (an unfinished 100 MB answer cannot be
   stopped another way in HTTP/1.1); the byte count for the caps is taken before each close (step 7).
4. **Upload phase:** new connections prepared as in 1 (the download ones are closed); each stream loops
   `POST /__up` with `Content-Length: 25000000`.
   - *Body (REQ-NH-0009):* generated while it is written, from one ChaCha8 stream per run (`math/rand/v2`
     `ChaCha8`, seeded once with 32 bytes from `crypto/rand`; go1.27.4 `chacha8.go:31, 54`, arm64 assembly in
     `internal/chacha8rand`), into each stream's own 64 KiB buffer. The generator is never reset or reseeded inside
     a run, so no block of any body repeats in the run, and no compressor or deduplicator finds anything, whatever
     its window (a 1 MiB buffer written again and again, as first proposed, would be found by any compressor with a
     window over 1 MiB, such as zstd long mode or brotli's large window). **Python sends ASCII zeros**
     (`cloudflare.py@ad3758c:334`); the Cloudflare engine sends ASCII zeros too (`genContent`,
     `BandwidthEngine.ts:129-135`); the requirement wins. Its CPU cost on the Pi 4 is measured with the rest (4.8).
   - *Count (M06-R5), in the same unit as the download: HTTP body bytes.* Each connection has two counting
     wrappers: one below TLS around the bound TCP connection (wire bytes read and written, the handshake
     included) and one above TLS, the `net.Conn` that `net/http` writes to (the engine dials TLS itself through
     `Transport.DialTLSContext`, ALPN `http/1.1` only, and returns this wrapper; plaintext bytes written, split
     into request header and body: a request's header bytes = its plaintext bytes − `Content-Length`). After each write above TLS returns
     (`tls.Conn.Write` has then written all its records below), the pair (wire offset, body offset) is kept as a
     checkpoint. `TCP_INFO.tcpi_bytes_acked` at `t0+2 s` and `t0+8 s` is a wire offset; it is mapped to a body
     offset by the last checkpoint at or below it and linear interpolation into the next write. With
     `DynamicRecordSizingDisabled` set (go1.27.4 `conn.go:900-903`) every record of a write carries up to 16 384
     plaintext bytes, so the interpolation is exact to one record's overhead (TLS 1.3: 5 header + 1 type + 16 tag =
     22 bytes; TLS 1.2 AES-GCM: 29; TLS 1.2 ChaCha20-Poly1305: 21), about 0.13 % of a record. The upload figure is
     the sum over the window's connections of body(end) − body(start). *Start* is the acknowledged offset at `t0+2 s`,
     or 0 for a connection opened inside the window. *End* is the acknowledged offset at `t0+8 s` or, for a
     connection that closes earlier (drop, stall, error answer, refusal), its `tcpi_bytes_acked` read just before it
     is closed, whichever comes first (the same reading as the drop record of 4.5 and the byte count of step 7;
     `TCP_INFO` stays readable on a reset socket until it is closed). So the bytes acknowledged before a drop count on
     the old connection and those after the reconnect on the new one, none twice. This removes both the TLS record overhead and the HTTP request headers from the acknowledged
     count, which a plain `tcpi_bytes_acked` difference would include (ciphertext, about 0.13 % more than the body
     bytes the download counts). **Python counts** bytes accepted by `send` (350-352), which includes data still
     in the socket buffer; **correct is** acknowledged bytes. Where `TCP_INFO` cannot be read (unexpected kernel),
     the acknowledged wire offset is wire bytes written − `SIOCOUTQ`, recorded as `upload_count = "outq"` in raw.
   - The unit is written into the raw `method` (`unit: "http_body"`, `upload_count`, `tls_record_overhead`).
   An answer other than 200 to a complete body is an error of that stream (4.5).
5. **Rate:** `bits_in_window / window_seconds` per direction, as an integer bit/s rounded down:
   `rate = floor(window_bytes × 8 × 10^9 / window_ns)`, computed with a 128-bit intermediate:
   `hi, lo := bits.Mul64(window_bytes, 8_000_000_000)`, then `rate, _ := bits.Div64(hi, lo, window_ns)`
   (`math/bits`, go1.27.4 `bits.go:470, 518`; exact in software on 32-bit targets). The plain 64-bit form
   overflows: `window_bytes × 8 × 10^9` passes 2^63 at about 1.15 × 10^9 bytes (≈ 1.5 Gbit/s over 6 s) and 2^64
   at about 2.31 × 10^9 bytes (≈ 3.1 Gbit/s), while REQ-RM-0025/1445 reach 10 Gbit/s (7.5 × 10^9 bytes in 6 s).
   `Div64` panics when `window_ns ≤ hi` (`bits.go:517-523`); `hi < window_ns` holds exactly when the quotient fits
   64 bits, that is for every rate below about 1.8 × 10^19 bit/s, so only `window_ns = 0` must be kept out. The
   engine gives a direction no value when its measured window is under 5 s (a suspended process, a deadline far
   off; `reason_code` `window_short`, added to B3), which also keeps the division away from 0. No float anywhere in
   the figure; the per-stream byte counters are atomic 64-bit values, correct on 32-bit ARM and MIPS (Generic First
   point 4). The window length is the measured one (deadline jitter included), not the nominal 6 s.
6. **HTTP/2:** not used for Cloudflare. Several HTTP/2 streams share one TCP connection and one congestion window, so
   "4 streams" would not be 4 TCP flows and the figure would not match the Python engine (REQ-RM-1038). REQ-RM-0026
   names HTTP/2 for the shared pool; the shared core (proposed M-17) may offer it to another engine. Difference
   recorded for F-02 (12, B8) and put to the decider (Q5).
7. **Byte count for the caps (M06-R7, M-05).** Not the rate's counters: what crossed the link. Just before any
   socket of the run is closed (transfer, probe, trace), its `TCP_INFO` is read: `bytes_down += tcpi_bytes_received`
   and `bytes_up += tcpi_bytes_sent` (x/sys `Bytes_received`, `Bytes_sent`, `ztypes_linux.go:505, 518`). These are
   TCP payload bytes, so TLS handshakes and record overhead, HTTP headers, warm-up requests and the part of a cut
   100 MB answer that reached the receive buffer but was never read are all in them, and `tcpi_bytes_sent`
   includes retransmissions (the box sent them). Bytes the server had already sent that were still in flight when
   the socket closed cannot be seen by the client; their upper bound is the receive window last advertised,
   `tcpi_rcv_wnd` at the cut (x/sys `Rcv_wnd`, 524; the kernel version that fills it is checked at implementation),
   summed over the cut sockets and reported beside the count as `bytes_down_inflight_max`. IP, TCP and link headers
   are not in either figure (section 8: about 3-5 %); whether M-05 adds them as a factor or reads interface
   counters is M-05's (expected from M-05, B10). Without `TCP_INFO` the count is the wire bytes read and written
   by the below-TLS wrapper (step 4) plus `SIOCINQ` (unread bytes in the receive queue) before close, marked `byte_count = "wrapper"` in raw.
   The budget check of M06-R7 uses the same count, read every 250 ms while a phase runs, plus the in-flight bound.

### 4.3 Latency, jitter, loaded latency, bufferbloat

- **Idle latency:** `N` TCP handshakes to the run's address and port 443, 80 ms apart, each timed from `connect`
  start to established, with the address already resolved (M06-R2). **Python includes** a DNS lookup in each
  timed span (`socket.create_connection((HOST, 443))` after `t0`, 237-239); **correct is** the handshake only. Each
  probe socket is bound like the transfers and closed at once (no TLS). `N` = 20 (Orchestrator, 2026-11-11, D3:
  Cloudflare's own count, about 1.6 s; Python's call site uses 5, 436), listed under Changed with its measured
  difference (9.6). Stored: `ping_us` = median, `jitter_us` = mean
  absolute difference of consecutive samples, both NULL without samples; jitter NULL with one sample.
- **Second latency figure (raw only):** the time to first byte of the warm-up `__down?bytes=0` minus the
  `server-timing` server time (Cloudflare's method, 3.2), recorded as `latency_http_ms` for comparison; never the
  stored ping (D3).
- **Loaded latency:** a probe every 500 ms (Python 266) during each phase, same handshake method. A sample counts
  only when its handshake started inside the phase's window `[t0+2 s, t0+8 s]` (M06-R3). **Python starts** the
  probe before the 4 TLS connections are even opened (443-446, 369-373) and keeps every sample, so samples taken
  during setup and ramp-up count as "loaded"; **correct is** window samples only. Stored: median per direction or
  NULL (REQ-CL-0140: never the idle value). A failed probe connect under load is counted in raw (`loaded_probe_fail`)
  and not turned into a value.
- **Grade:** R-01's grade function on idle and the sampled directions only (REQ-CL-0196, KF-0125); NULL when no
  direction was sampled.

### 4.4 Concurrency and the run's states

One goroutine per stream and phase, one probe goroutine, one coordinator; all under one `context.Context` given by
the runner. States: `prepare → idle_latency → download → upload → done`, and from any state `refused`, `cancelled`,
`stopped_by_gate`, `budget_reached`, `failed`. No package-level state (**Python keeps** the source address and the
peer list in module globals, 41-42, 424-426, safe only because the runner holds a lock; **correct is** per-run
state, clean-code rule "no hidden state"). On cancel or gate stop every connection's deadline is set to now, so a
blocked read returns at once (M06-R10; **Python waits** up to the 15 s socket timeout and a 20 s join deadline and
may leave daemon threads holding sockets, 387-393).

| Rate above 1.05 × the link's negotiated speed | the direction gets no value, its cause `impossible_result` (status rule below: `partial` when the other direction was measured); the figure only in the error text and the log | dropped silently: status error with **no** error text when no transfer error happened (408-413, 481, 495; NF-11) |
| Budget reached (M06-R7) | the phase stops. In the download phase: failed `data_budget_reached`, no values, the upload not started. In the upload phase after a measured download: `partial` (M06-R13), cause `data_budget_reached` in raw. Before the upload phase, when the remaining budget is below the upload's estimate (8): the upload is not started, `partial` with the same cause | not possible |
| Gate stop (traffic of other devices, Phase 0) | aborted: no values (roadmap 646 "no partial result is saved"), `reason_code` from M-04 | M-04's matter |

**Status rule (Orchestrator, 2026-11-11, D5; recorded by M-04, B2):** a direction is *measured* when all 4 streams
took part, every stream covered at least 95 % of its window (drops that reconnected quickly are fine and shown) and
its rate passed the plausibility check; otherwise that direction *failed* with its cause (`connect_failed`,
`stream_loss`, `impossible_result`, `window_short`, `data_budget_reached`). Both measured: `ok`. One measured, the
other failed: status `error`, `reason_code` `partial`, the measured direction's values kept, the failed one NULL,
its cause in raw (`failed_direction: {direction, cause}`), never `ok` (M06-R13, KF-0224). Both failed: status
`error`, no values, the first failed direction's cause as `reason_code` (the other's in raw). A refusal (D1) and a
gate stop override this rule as the table says. Dropped-and-reconnected streams are logged at info level
(REQ-CL-0431) as one event `cloudflare_stream_dropped` with the class, and their number is stored
(`streams_dropped` in raw, plus `streams_down`/`streams_up` = streams that took part).

### 4.7 Binding and the link (KF-0231, REQ-RM-0027, REQ-TS-0059, REQ-TS-0156)

Every socket (transfers, probes, trace) is made by F-04d `Dial(network, address, link, local_ip?)`, which sets
`SO_BINDTODEVICE` before `connect` and the source address when given. Without an address on the asked link the
runner decides (roadmap 4.29: the default route is then the link described); the engine reports the link and
address its sockets really had (`getsockname`, `SO_BINDTODEVICE` value). **Python binds** only a source address
and nothing at all when there is none (`cloudflare.py@ad3758c:79-83, 225-241`; private audit 2026-11-10, engines
item 4). The link's negotiated speed for the plausibility check comes from F-04d link facts; for a PPP or VLAN link
the speed of the lower Ethernet link (Python reads `/sys/class/net/ppp0/speed`, which has none, so its check is off
on PPPoE; Blocked B5). CA roots: the system's bundle found at run time (Go's own search list); the path used is in
the self-test.

### 4.8 Resources on the Pi 4 (to measure, not claimed)

Memory: 4 × 64 KiB receive buffers, 4 × 64 KiB upload body buffers (filled from the ChaCha8 stream as they are
written), the per-connection checkpoint lists of 4.2 step 4 (one entry per write, bounded by trimming entries below
the last sampled acknowledged offset), TLS state per connection; budget < 4 MiB of heap during a run, zero
allocations per read or write in the hot loop (benchmark). The ChaCha8 generation for the upload body is measured
with the TLS cost (it competes for the same cores). CPU: the Pi 4's Cortex-A72 has no AES or PMULL
instructions, so Go offers ChaCha20-Poly1305 first in TLS 1.3 (`defaults.go:114-118`, `cipher_suites.go:366`), with
NEON ChaCha20 and portable Poly1305; OpenSSL's default TLS 1.3 list puts AES-256-GCM first. Both are only the
client's offer: in TLS 1.3 the server selects the suite (RFC 8446 4.1.1, 4.1.3), and which suite Cloudflare's edge
selects for Go's offer and for CPython/OpenSSL's is not known. What counts is the suite negotiated: the native
engine records it per run (`tls.ConnectionState().CipherSuite`, M06-R9); the Python side is observed as in 6
step 2. The README records
77-88 % CPU for TLS at 910 Mbit/s on the Pi 4 (`README.md@ad3758c:125`). Recorded per run: cipher, `cpu_peak_pct`;
the gate figure: CPU and rate at line speed, native against Python, same box and day (QB4). If the native engine is
CPU-bound below the line rate on the Pi 4, that is a known limit with numbers, not a pass.

### 4.9 Identity and headers (M06-R8)

Requests carry only `Host`, `User-Agent` (from C-05 `useragent.Transport`, component code `cloudflare`: the own
identity `NetworkMeasureBox/<version> (cloudflare)` or the owner's custom value, `user_agent_custom` = 1 then), `Accept:
*/*`, `Content-Type: application/octet-stream` and `Content-Length` on uploads. **Python sends** a HeadlessChrome
agent as a fallback (86-91) and imitates a browser page with `Origin`, `Referer`, `Sec-Fetch-Mode`,
`Sec-Fetch-Site` "to avoid Cloudflare WAF 429 rate-limiting" (181-189, c2fca70); **correct is** no imitation: if
Cloudflare refuses the box under its own name, the refusal is reported (4.5), never worked around (D2).
The one recorded request (1.3) was answered 200 under the own name; the private findings of 2026-11-10 (Wi-Fi
section) record a 403 for a plain command-line client on the box on another occasion, so a refusal of the own
identity at full transfer sizes is possible and is tested on the Pi 4 (T-M06-31) before the engine replaces Python.

## 6. The TLS drops on the Pi 4 (REQ-RM-1257, KF-0286): plan to show whether OpenSSL was the cause

1. **What is recorded on both sides.** Native: every drop with its Go error class (`bad_record_mac` alert,
   `record_header`, `unexpected_eof`, `reset`, `stall`), the time into the phase, bytes read so far on that stream,
   and `TCP_INFO` at that moment (`retrans`, `lost`, `rtt`, `rcv_space`), plus the negotiated cipher. Python: its
   message string, already stored as `recovered_tls_streams` and in the log.
2. **Same box, same day, interleaved.** On the Pi 4 (owner point 5: backup, way back, own-action window), runs
   alternate Python, native default (TLS 1.3, Go's offer) and native with AES-GCM. Each arm is described by the
   suite actually negotiated, not by the client's offer (the server selects, RFC 8446 4.1.3). Native runs record it
   (M06-R9). Python does not store it (`cloudflare.py@ad3758c` has no cipher read; `HTTPSConnection` without a
   context, 228, so CPython's default HTTPS context), so before and after each Python series a one-off check on the
   box with the same CPython, OpenSSL and default context connects to `speed.cloudflare.com` and records
   `ssl.SSLSocket.cipher()` and `version()` (handshake only, own agent, no transfer; kept in `~/nmb-logs`). The
   native arm whose negotiated suite equals Python's is the one compared with Python (OpenSSL against Go with the
   cipher equal); the other arm separates the cipher. The report names the suite of every arm. Go cannot
   choose TLS 1.3 suites (`tls.Config.CipherSuites` applies to TLS 1.2 only) and go1.27.4 has no `GODEBUG` switch
   for their order (`internal/godebugs/table.go`: only `tlsmaxrsasize`, `tlsmlkem`, `tlssecpmlkem`, `tlssha1`,
   `fips140ems` remain), so the AES arm is a test-only setting `MaxVersion: TLS 1.2` with the
   `ECDHE_*_WITH_AES_256_GCM_SHA384` suites (the roadmap already ruled the TLS version out as the cause). At least
   30 runs per arm, spread over a day, same link and binding. The AES arm separates "OpenSSL" from "cipher or CPU
   load".
3. **Reading the outcome.** Drops per run with a 95 % interval per arm. (a) Python drops and both native arms do
   not: the cause is in the OpenSSL/CPython read path, written into KF-0286. (b) Native arms drop too, with
   `bad record MAC`: the data was damaged below TLS (driver, DMA, offload) and passed the TCP checksum; then a
   capture of headers only (`tcpdump -s 128` on the box, kept in `~/nmb-logs`, never committed) at a drop and the
   kernel log are the next step. (c) Native drops are `unexpected_eof`/`reset`: the far end or the path closed the
   stream; `cfL4` and `TCP_INFO` show which. Each case is recorded in KF-0286 and `docs/TESTING.md`.
4. **The result never hides a drop:** 4.5 status rule and the raw record per stream.

## 8. Data use per run (for the data caps, M-05)

Per direction ≈ line rate × 8 s plus the cut-off tail of the open answers (what reached the receive buffers
unread, plus what was still in flight: at most a receive window per stream) and TLS/TCP/IP overhead (about 3-5 %);
latency probes and metadata are a few kilobytes. In megabytes per run (rate in Mbit/s ×
8 s / 8 = MB):

| Line (down/up, Mbit/s) | Download | Upload | Per run | 24 runs a day |
| :--- | ---: | ---: | ---: | ---: |
| 1000/300 | ≈ 1000 MB | ≈ 300 MB | ≈ 1.3 GB (README: about 1.2 GB) | ≈ 31 GB |
| 100/20 | ≈ 100 MB | ≈ 20 MB | ≈ 120 MB | ≈ 2.9 GB |
| 20/5 (mobile) | ≈ 20 MB | ≈ 5 MB | ≈ 25 MB | ≈ 0.6 GB |

The engine gives M-05 an estimate before the run:
`EstimateBytes(downBps, upBps) = (downBps + upBps) × 8 s × 1.05 / 8 + streams × (1 + reconnects_per_stream) × rmem_max
+ 1 MiB`. The middle term bounds the unread tails and in-flight bytes of every download connection that can be cut
(4 streams, each cut at most 3 times: at `t0+8 s` and at up to 2 drops); `rmem_max` is the kernel's largest TCP
receive buffer (third field of `/proc/sys/net/ipv4/tcp_rmem`, read at run time; Go sets no `SO_RCVBUF`, so
autotuning may grow to it), the same bound the budget check of M06-R7 counts while a phase runs. Which rates go in
is M-05's: the link's last measured rates, and for a first run without them not the port's negotiated speed (a
gigabit port on a 20 Mbit/s line would estimate about 1.3 GB and could keep a small cap from ever allowing a first
run) but something closer to the line, such as the declared plan speed or a short probe (expected from M-05, B12).
The engine then counts the real bytes (`bytes_down`, `bytes_up`: TCP payload received and sent per socket from `TCP_INFO`, warm-up,
unread tails and retransmissions included, with `bytes_down_inflight_max` beside them; 4.2 step 7) and stops a phase
when the budget is reached (M06-R7). The table's figures are what the count should come to; IP/TCP header bytes are
M-05's (B10). On a metered link without a decision the
engine does not start (owner point 14). How often runs happen is the user's choice (Owner, 2026-11-11, D4):
`cloudflare_interval_min` keeps Python's range 0..10080 and any schedule interval is allowed; the data caps (M-05)
and the refusal pause (D1) are the only limits for Cloudflare (Ookla's own hourly rule is Ookla's only), and a test
a person starts is never held back except by a refusal pause. The 24-runs column is an example, not a limit. The
manual's figure is this table (REQ-RM-1381).

## 10. Security check (Quality Bar 7)

- **Outside inputs:** HTTP status, headers and bodies from the Cloudflare edge, DNS answers. Headers: length limits
  (a header block of at most 16 KiB, `MaxResponseHeaderBytes`), allowed characters and types checked as in 4.1;
  unknown headers ignored; download bodies are counted and discarded, never parsed; trace body ≤ 4 KiB, parsed
  line by line; `Retry-After` bounded; `server-timing` numbers bounded and finite. No value from outside builds a
  command, a path or a log format string; logged values are escaped by C-03.
- **TLS:** certificate verification always on (no option to turn it off), system roots only, TLS 1.2 minimum, host
  name `speed.cloudflare.com`; no `InsecureSkipVerify` anywhere in the package (gate grep).
- **Privileges:** none of its own; `SO_BINDTODEVICE` needs `CAP_NET_RAW` (F-04d 4.1.7; P-04's profile for the speed
  engine). No listening socket, no file written, no `nmb.conf` read (the runner passes what is needed). Runs in the
  speed engine's sandbox (6B.5).
- **Secrets:** none used; the custom user agent is the owner's setting and is not a secret.
- **Resource limits:** fixed buffers, deadlines on every socket, at most 4 streams + 1 probe + 2 reconnects per
  stream; total run deadline 60 s.
- **Privacy:** the box's public address and the client place reported by Cloudflare stay on the box (raw record),
  coordinates are not kept; R-04 masks the client address in outside bundles (its rule).

## 12. Blocked (contract differences, not designed around)

- **B1 (F-04a 3.5.8):** `[speedtest] user_agent_mode` still lists the browser presets; C-05 B2 removes the mode key
  and the presets (owner, bb0a553). M-06 uses only `useragent.Transport`; F-04a must follow C-05.
- **B2 (F-04b 3.4/3.5.5, M-04): partial runs, decided (Orchestrator, 2026-11-11, D5); the contracts must follow.**
  A run with one direction measured and the other failed is status `error`, `reason_code` `partial`, the measured
  direction kept, the failed one NULL, never `ok`; one rule for all engines, recorded by M-04. F-04b's `status`
  CHECK (`ok`, `skipped_busy`, `error`, F-04b 267) needs no change. F-04b must (a) add `partial` to
  `spec/codes/speed_reason.json` and (b) say in 3.5.5 that an `error` row with `reason_code` `partial` carries the
  measured direction (its text forbids values only on skipped and aborted rows, 412-413, and reads NULL as
  "direction not measured", 374). Expected from M-04: the rule, the raw `failed_direction` field, and that a refusal
  (D1) overrides it (the refused run stored as failed with no speed value, as 4.5 does); if M-04 decides refusals
  otherwise, 4.5 follows M-04. R-01 and every report read `reason_code`, so a `partial` row never counts as a
  successful test.
- **B3 (F-04b):** the reason codes of 5 (`window_short`, `partial` and `no_source_address` among them, 4.1, 4.2 step 5, 4.5) are not in `spec/codes/speed_reason.json` yet; and the raw record schema

- **B7 (M-05, M-04): the refusal pause, decided (Orchestrator, 2026-11-11, D1), in no draft yet.** Expected from
  M-05: `Pause.Refused(engine, retryAfter)` starting a pause of 30 min doubling to 4 h, at least `Retry-After`,

- **B8 (F-02, wording):** REQ-PP-0081 names 25/50/100 MB tiers and REQ-RM-0026 names HTTP/2; this brief keeps
